# 公告管理与身份同步设计

## 目标

为部长及以上身份的用户提供公告新增、修改和删除能力，并让公开公告页读取数据库中的已发布公告。公告编辑器左侧编辑原始 Markdown，右侧使用与正式公告详情相同的渲染组件实时预览。

身份登录成功后，系统同步身份提供方返回的用户资料、账号状态和最后登录时间。角色遵循“只升不降”：保留本地手工提升的角色，只在身份角色权限更高时提升。用户同步必须原地更新现有记录，不改变 `users.id` 主键。

## 现状

- 后端已有 `Announcement` 模型和基础 CRUD 接口。
- 前端已有 `/admin/announcements` 管理页和公告 API 请求封装，但公开公告页仍读取静态 Markdown 清单。
- 管理页已有编辑框和预览区，但预览使用独立的基础 `MarkdownIt` 配置，与正式公告渲染效果可能不一致。
- 写接口已有 `manager` 校验，但管理路由缺少可靠的前端访问保护。
- 身份登录会通过 `provider + provider_id` 查找用户并更新部分资料和 `last_login`；当前角色已采用取最高权限的策略，但账号状态和完整缓存刷新仍需统一处理。

## 角色与权限

外部身份统一映射为以下内部角色：

- `member`：普通成员。
- `staff`：干事或部门成员。
- `manager`：副部长、部长、社长、管理员及其以上身份。

公告新增、修改、删除以及草稿读取仅允许 `manager`。前端根据当前用户角色展示管理入口并保护管理路由，后端仍是最终权限边界，每个管理请求都重新核对数据库中的最新角色。

## 公告接口

### 公开读取

- `GET /announcement/` 默认只返回已发布公告，按发布时间或创建时间倒序排列。
- `GET /announcement/<id>` 对普通访问者只返回已发布公告。
- 不存在或当前用户不可见的公告统一返回 `404`，避免泄露草稿信息。

### 管理读取与写入

- `GET /announcement/?include_unpublished=true` 需要 `manager` 权限，返回草稿和已发布公告。
- `POST /announcement/` 创建公告，校验标题和 Markdown 内容非空。
- `PUT /announcement/<id>` 原地更新现有记录，不删除重建，因此公告主键保持不变。
- `DELETE /announcement/<id>` 删除指定公告，并在前端执行二次确认。
- 未登录返回 `401`，权限不足返回 `403`，非法输入返回 `400`，记录不存在返回 `404`。

## 前端体验

公开公告页改用公告 API 获取列表和详情，并具备加载、失败、重试和空列表状态。`manager` 用户在公告页看到“管理公告”入口，其他用户不显示。

管理页保留列表、创建、编辑和删除工作流。编辑状态包含标题输入和 Markdown 编辑区：

- 桌面端左侧为原始 Markdown，右侧为实时渲染结果。
- 移动端改为上下排列，避免狭窄双栏。
- 右侧复用正式的 `MarkdownComponent`，保证预览和发布效果一致。
- 保存期间禁用重复提交；保存失败时保留当前编辑内容并显示错误。
- 删除使用应用内确认对话框，成功后刷新列表。

管理路由标记为需要登录和 `manager` 权限。路由进入前恢复并验证会话；未登录用户进入登录流程，已登录但权限不足的用户进入拒绝访问状态。

## 身份登录同步

身份提供方认证成功后，从经过上游认证流程取得的 JWT 或 OIDC 用户信息中提取用户标识、资料、角色和账号状态。同步流程如下：

1. 使用 `provider + provider_id` 查找本地用户。
2. 已有用户原地更新；不创建替代记录，不改变 `users.id`。
3. 身份资料字段仅在来源值非空且不会违反唯一约束时更新。
4. 账号状态仅在身份声明明确提供时更新；声明缺失时保留本地值。
5. 新角色取本地角色和身份角色中权限较高者，防止身份角色降低覆盖本地手工提升。
6. 更新成功登录时间 `last_login`。
7. 使用同步后的本地用户数据刷新认证缓存并签发本站访问令牌和刷新令牌。

账号状态支持常见布尔声明（如 `is_active`、`active`、`enabled`）和可明确归一化的状态字符串。无法识别的状态不覆盖本地值。

## 数据一致性

用户和公告更新均使用 ORM 实例的原地保存操作。任何资料字段冲突或持久化失败都不应创建第二个用户，也不应改变主键。用户同步完成后，JWT 载荷、Redis 用户缓存和登录响应中的用户信息必须来自同一份最新本地记录。

## 错误处理

- 公告列表或详情加载失败时展示可重试状态，不以空列表掩盖请求错误。
- 写操作失败时显示后端错误消息；`401` 触发重新认证，`403` 显示权限不足。
- 身份资料的单个可选字段缺失不会阻断登录。
- 身份唯一标识缺失、用户持久化失败或账号明确不可用时，不签发本站令牌，并记录不包含敏感令牌内容的服务端错误。
- 不记录完整外部 JWT 或密码登录响应，避免敏感声明和令牌进入日志。

## 测试与验收

后端自动化测试覆盖：

- 部长、副部长、社长和管理员身份归一化为 `manager`。
- 登录同步允许角色提升但拒绝角色降级。
- 已有用户同步后 `users.id` 不变，资料、明确账号状态和 `last_login` 正确更新。
- 身份状态缺失时保留本地状态。
- 普通用户无法新增、修改、删除公告或读取草稿。
- 管理员可以完成公告 CRUD，修改操作保持公告主键不变。
- 公开列表和详情不返回草稿。

前端验证包括严格 TypeScript 检查和生产构建。浏览器验收覆盖普通用户与 `manager` 两种身份、公告 CRUD、正式渲染一致性、桌面双栏、移动端上下布局，以及加载和失败状态。

## 非目标

- 不实现公告版本历史、多人协同编辑、附件上传或审批流。
- 不迁移或重建现有用户主键。
- 不改变本地手工提升角色的优先级。
- 不继续维护数据库与静态公告文件的双写机制。
