## 第一部分：后端开发全景

### 1.1 比喻：网站 = 一家餐厅

把整个网站想象成一家餐厅：

| 网站部件 | 餐厅类比 | 职责 |
|---------|---------|------|
| 浏览器 | 顾客 | 点菜、用餐、看菜好不好吃 |
| 前端页面 | 菜单、餐桌 | 展示给顾客看的东西 |
| **后端** | **后厨** | 接单、做菜、把菜端到窗口 |
| **数据库** | **食材仓库** | 存放所有原料（数据） |
| API | 点菜的规矩 | 顾客用什么格式点、厨房按什么格式上 |

**这个比喻的局限**：餐厅后厨只服务前厅；后端还要服务**多个端**——网页、手机 App、别的服务器。同一个后端可以被多种"顾客"调用。

### 1.2 后端具体做什么（三大职责）

后端程序运行在服务器上，负责三件事：

| 职责 | 做的事 | 比喻 |
|------|--------|------|
| **接收请求** | 拿到前端发来的 HTTP 请求（URL、参数、数据） | 接单员记下顾客的点单 |
| **处理业务** | 校验数据、算逻辑、查/写数据库、做权限判断 | 厨师按菜谱做菜 |
| **返回响应** | 把结果封装成数据（通常是 JSON）返回给前端 | 把菜端到窗口 |

**核心结论**：后端不负责"好不好看"（那是前端的事），后端负责"对不对、快不快、安不安全"。

### 1.3 一次完整请求的旅程（原理 + 流程）

用户点击"登录"按钮后，后台发生了什么：

```
① 浏览器  → 发 HTTP 请求（POST /auth/login，带上用户名密码）
② 服务器  → Nginx 接收，转发给后端进程
③ Flask  → 路由匹配：这条 URL 由哪个函数处理？
④ 业务层  → 校验密码是否正确（哈希比对）
⑤ 数据库  → 查询 users 表，取出该用户的密码哈希
⑥ 后端    → 比对通过，生成 JWT 令牌
⑦ 后端    → 返回 JSON：{token: "..."}
⑧ 浏览器  → 收到响应，保存 token，跳转首页
```

**数据流**：浏览器 → 网络 → Nginx → Flask（路由→业务→数据库）→ 返回数据 → 浏览器。每经过一层，数据都被"加工"一次。

### 1.4 后端技术栈全景（你在项目里用到的）

你的 OJ 项目后端用了这些，先认识它们各自是什么：

| 技术 | 作用 | 比喻 |
|------|------|------|
| Flask 3 + Flask-RESTX | Web 框架：处理 HTTP、路由、API 封装 | 后厨的整套灶台 |
| PostgreSQL | 关系型数据库：存用户、题目、提交记录 | 食材仓库 |
| Peewee | ORM：用 Python 对象操作数据库 | 仓库管理员，帮你搬货 |
| Redis | 内存数据库：缓存、限流、JWT 黑名单 | 灶台边的调料架（取用最快） |
| Gunicorn | WSGI 服务器：让 Flask 能同时服务多请求 | 多个厨师同时炒菜 |
| Glot.io | 外部判题服务 | 外卖送检的第三方检验机构 |

## 第二部分：后端框架（Flask）

### 2.1 什么是后端框架？为什么需要它？

**定义**：后端框架（Backend Framework）是一套写好的"半成品程序"，它帮你处理 Web 开发的通用琐事，你只需填上自己的业务逻辑。

**没有框架时你要自己写**：怎么监听端口、怎么解析 HTTP 请求、怎么拼响应报文、怎么处理并发、怎么做路由……这些和业务无关却极其繁琐。

**有了框架后你只写**：`@app.route('/auth/login')` 下面那个函数里的业务逻辑。

| 痛点 | 没有框架 | 有框架（Flask） |
|------|---------|----------------|
| 监听 HTTP 请求 | 自己写 socket 服务 | `app.run()` 一行搞定 |
| 解析请求数据 | 手写解析 HTTP 报文 | `request.get_json()` 直接拿到字典 |
| 路由分发 | 自己 if/else 匹配 URL | 装饰器 `@app.route()` |
| 并发处理 | 自己搞线程池 | 配合 Gunicorn 自动多进程 |

**比喻**：框架 = **半成品厨房**。灶台、水管、排烟罩都装好了，你只负责炒菜（写业务），不用自己砌灶台。

**这个比喻的局限**：框架虽然省事，但**不是万能的**——你仍需理解 HTTP、数据库、并发这些底层原理，否则遇到性能问题、安全漏洞时会无从下手。

### 2.3 主流后端框架对比（帮你选型）

| 框架 | 语言 | 特点 | 适合场景 | 比喻 |
|------|------|------|---------|------|

| FastAPI | Python | 自动生成文档、性能高、类型提示 | 现代 API 服务、异步高并发 | 现代化快餐店：出餐快、有菜单 |

**你的项目为什么用 Flask**：你的 OJ 项目规模适中，Flask 轻量灵活，配合 Flask-RESTX 组织 API 非常顺手；且 Python 生态（判题、数据处理）对你有优势。**注意**：若未来业务暴涨需高并发异步，可平滑迁移到 FastAPI（同为 Python，思路相通）。

### 2.4 Flask 的核心机制（原理）

**路由（Routing）**：把"URL + 请求方法"映射到"处理函数"。

```python
from flask import Flask, jsonify, request

app = Flask(__name__)

@app.route('/hello', methods=['GET'])
def hello():
    return jsonify({'message': '你好，世界！'})

if __name__ == '__main__':
    app.run(host='0.0.0.0', port=5000, debug=True)
```

保存为 `app.py`，执行 `python app.py`，浏览器访问 `http://localhost:5000/hello` 会看到 `{"message": "你好，世界！"}`。

**逐行拆解**：

| 代码 | 作用 |
|------|------|
| `from flask import Flask` | 导入 Flask 类 |
| `app = Flask(__name__)` | 创建 Flask 应用实例，`__name__` 用于定位资源 |
| `@app.route('/hello', methods=['GET'])` | 装饰器：注册路由，规定 URL 和允许的方法 |
| `def hello():` | 处理函数：Flask 收到匹配请求后调用它 |
| `return jsonify({...})` | 把字典转成 JSON 响应返回 |
| `app.run(host='0.0.0.0', port=5000)` | 启动开发服务器；`0.0.0.0` 表示允许外部访问 |

### 2.5 请求与响应（Request 和 Response）

Flask 把 HTTP 请求封装成 `request` 对象，你在函数里直接读：

| 取数据的场景 | 代码 | 例子 |
|------------|------|------|
| URL 里的参数 `/users?page=2` | `request.args.get('page')` | 分页参数 |
| URL 路径里的参数 `/users/42` | `@app.route('/users/<int:uid>')` | 用户 ID |
| POST 提交的 JSON 数据 | `request.get_json()` | 登录表单 |
| 请求头（如 token） | `request.headers.get('Authorization')` | JWT 认证 |
| 客户端 IP | `request.remote_addr` | 限流、日志 |

**注意安全最佳实践**：`request.get_json()` 可能返回 `None`（当请求体不是合法 JSON 时），使用前必须判空。

### 2.6 分层架构（后端最重要的设计思想）

写后端**不能把所有代码堆在一个函数里**。你的项目用的是经典三层架构：

```
┌─────────────────────────────────┐
│ Controller 层（迎宾员）           │
│ 接请求、传参数、返回响应、不写业务 │
├─────────────────────────────────┤
│ Service 层（厨师）               │
│ 业务逻辑：校验、计算、调数据库    │
├─────────────────────────────────┤
│ Model/Repository 层（仓库管理员） │
│ 只管数据库增删改查               │
└─────────────────────────────────┘
```

**职责划分**：

| 层 | 职责 | 不做什么 |
|----|------|---------|
| Controller | 解析请求、调用 Service、封装响应、处理异常 | 不写 SQL、不算业务 |
| Service | 业务规则、事务控制、编排多个 Model | 不直接拼 SQL 细节 |
| Model | 表映射、简单 CRUD | 不接收请求、不做页面逻辑 |

**好处**：职责清晰、可测试（每层可单独测）、可替换（换数据库只改 Model 层）、可复用。

**你的项目里对应**：`controllers/ → services/ → models/`，加上 `middleware/`（JWT 验证、角色权限、限流）和 `interfaces/`（抽象接口 + 依赖注入）。这正是面试常问的"分层架构"。

### 2.7 依赖注入（Dependency Injection, DI）

**定义**：对象不自己 new 依赖，而是由外部（容器）把依赖送进来。

```python
class UserService:
    def __init__(self, user_repo):   # 依赖从外面传进来
        self.user_repo = user_repo

# 不使用 DI：
user_service = UserService(MySqlUserRepo())

# 使用 DI（由容器/外部决定传哪个）：
user_service = UserService(MockUserRepo())   # 测试时换假的
user_service = UserService(MySqlUserRepo())  # 生产用真的
```

**比喻**：厨师不用自己开农场。菜（依赖）由采购部（容器）按时送进厨房，厨师只声明"我要什么菜"。

**这个比喻的局限**：真实的 DI 容器还会管理对象的生命周期（单例/每次新建）、自动解析嵌套依赖，比"采购部送菜"复杂得多。

**为什么 DI 重要**：**测试**。没有 DI，测试时连数据库都得真的连；有了 DI，测试时注入一个返回假数据的对象即可。你的项目 `interfaces/` + `core/` DI 容器就是这个思想的实现。

### 2.8 蓝图（Blueprint）—— 组织大型 Flask 项目

一个真实项目会有几十个接口，全写在一个 `app.py` 里会爆炸。**蓝图**帮你把路由分组：

```python
# auth_routes.py —— 用 Blueprint 组织"认证"相关的路由
from flask import Blueprint

auth_bp = Blueprint('auth', __name__, url_prefix='/auth')

@auth_bp.route('/login', methods=['POST'])
def login():
    return {'message': '登录接口'}

# app.py
from auth_routes import auth_bp
app.register_blueprint(auth_bp)   # 注册蓝图
```

访问 `/auth/login` 就命中 `login()`。**比喻**：蓝图像**餐厅的部门**——冷菜间、热菜间各管一摊，最后统一由店长（app）管理。**注意**：Flask 蓝图管"URL 分组"，Flask-RESTX 的 `Api` 管"接口文档化"，两者各司其职；你的项目在蓝图之上再挂 RESTX 组织 API 文档。

## 第三部分：数据库（PostgreSQL）

### 3.1 什么是数据库？为什么要用它？

**定义**：数据库（Database）是**专门用于存储、管理和查询数据的软件**。

**不用数据库用文件不行吗**？行，但会有一堆问题：

| 问题 | 用普通文件 | 用数据库 |
|------|-----------|---------|
| 并发访问 | 两个请求同时写会互相覆盖 | 事务 + 锁机制保证安全 |
| 查询 | 全文件扫描，慢 | 索引 + SQL，毫秒级 |
| 一致性 | 转钱时扣了 A 没加 B | ACID 事务保证要么全成要么全不成 |
| 数据安全 | 断电可能损坏 | 日志 + 崩溃恢复 |

**比喻**：文件 = **散落一地的纸**；数据库 = **带目录、有管理员、能多人在线操作的正规档案库**。

### 3.2 关系型数据库基础（表、行、列、主键、外键）

PostgreSQL 是**关系型数据库**：数据存在"表"里，像 Excel。

| 概念 | 含义 | 比喻 |
|------|------|------|
| 表（Table） | 一类实体的集合 | 一个表格 |
| 行（Row） | 一条记录 | 表格里的一行 |
| 列（Column） | 一个字段 | 表格里的一列 |
| 主键（Primary Key） | 唯一标识一行的字段 | 学号，不能重复 |
| 外键（Foreign Key） | 指向别表主键的字段 | 学生的班级号指向班级表 |

**你的 OJ 项目 6 张表**：

```
users（用户表）          problems（题目表）
  ├─ id PK               ├─ id PK
  ├─ username            ├─ title
  └─ role                └─ difficulty
        │
testcases（测试用例表）   user_codes（用户代码表）   submissions（提交记录表）
  ├─ id PK                ├─ id PK                   ├─ id PK
  ├─ problem_id FK        ├─ user_id FK              ├─ problem_id FK
  └─ input/output         └─ code                    ├─ user_id FK
                                                     └─ status
announcements（公告表）
  ├─ id PK
  └─ content
```

### 3.3 SQL 增删改查（CRUD）

SQL（Structured Query Language，结构化查询语言）是操作关系型数据库的标准语言。

| 操作 | 语法示例 | 说明 |
|------|---------|------|
| 查 | `SELECT * FROM users WHERE username='z'` | 按条件查 |
| 增 | `INSERT INTO users (username, role) VALUES ('z', 'member')` | 插入一行 |
| 改 | `UPDATE users SET role='manager' WHERE username='z'` | 更新 |
| 删 | `DELETE FROM users WHERE id=42` | 删除 |

**比喻**：SQL = 向图书管理员提问。"`SELECT * FROM users WHERE username='z'`" = "把用户名是 z 的用户所有信息给我"。

**JOIN（多表联查）**：把多张表按关联字段拼起来。

```sql
-- 查出每个提交记录对应的题目标题
SELECT s.id, s.status, p.title
FROM submissions s
JOIN problems p ON s.problem_id = p.id
WHERE s.user_id = 1;
```

### 3.4 ORM（Peewee）—— 用 Python 对象操作数据库

**定义**：ORM（Object-Relational Mapping，对象关系映射）把数据库表映射成编程语言的类，让你用对象操作代替手写 SQL。

**你的项目用的 Peewee**：

```python
from peewee import *

db = PostgresqlDatabase('oj', user='z', password='***', host='localhost')

class User(Model):
    username = CharField(unique=True)
    role = CharField(default='member')

    class Meta:
        database = db

# 增
User.create(username='alice', role='manager')
# 查
user = User.get(User.username == 'alice')
# 改
user.role = 'staff'
user.save()
# 删
user.delete_instance()
```

| 手写 SQL | Peewee 写法 |
|---------|-------------|
| `SELECT * FROM users WHERE username='alice'` | `User.get(User.username == 'alice')` |
| `INSERT INTO users (...) VALUES (...)` | `User.create(...)` |
| `UPDATE users SET role='staff'` | `user.role = 'staff'; user.save()` |

**好处**：防 SQL 注入（自动参数化）、跨数据库可移植、代码可读。

**核心安全原理——参数化查询**：ORM 把**用户输入当"数据"而不是"SQL 代码"**处理，从根本上杜绝 SQL 注入。**比喻**：点单时，顾客输入的"宫保鸡丁"只被当作菜名，绝不会被当作"后厨操作指令"执行。

### 3.5 索引（Index）—— 查询加速的秘诀

**问题**：`SELECT * FROM submissions WHERE user_id=1` 在 1000 万行数据里逐行扫描，要几秒。

**解决**：给 `user_id` 建索引，查询变成走 B+ 树查找，毫秒级。

```sql
CREATE INDEX idx_submissions_user ON submissions (user_id);
```

**比喻**：索引 = 书的**目录**。没目录查内容要逐页翻（全表扫描）；有目录直接跳到对应页。

**这个比喻的局限**：目录不会拖慢翻书，但索引**会占用磁盘空间**，且**每次增删改都要更新索引**，写变慢。所以索引不是越多越好，只给**高频查询的字段**建。

**你的项目里就在用**：`submissions` 表按 `(problem_id, status)` 建的复合索引，正是为了加速"按题目+状态查提交记录"这个高频查询。

### 3.6 事务与 ACID —— 要么全成功，要么全失败

**定义**：事务（Transaction）是一组数据库操作，**要么全部成功，要么全部失败回滚**。

**转账场景**（经典例子）：
```python
with db.atomic():          # 开启事务
    a.balance -= 100       # 扣 A 的钱
    b.balance += 100       # 加 B 的钱
    # 若中途出错，自动回滚，A 的钱不会少
```

**ACID 四要素**：

| 字母 | 含义 | 解释 | 比喻 |
|------|------|------|------|
| A | Atomicity 原子性 | 全成或全败 | 一锅菜要么整盘好要么重炒 |
| C | Consistency 一致性 | 数据始终合法 | 总金额不变 |
| I | Isolation 隔离性 | 事务互不干扰 | 各桌点菜互不影响 |
| D | Durability 持久性 | 提交后不丢失 | 菜谱记在案板上，断电不忘 |

### 3.7 数据库连接池（Connection Pool）

**问题**：每次查询都新建数据库连接（建立 TCP + 鉴权）很慢；并发时连接数还可能爆掉。

**解决**：**连接池**——预先建立一批连接放池子里，用完归还，重复使用。

**你的项目里就在用**：`DB_MAX_CONNECTIONS=20` 就是连接池上限。并发超过 20 个请求时会排队等待。

**比喻**：连接 = 快递车。每趟都去买新车（新建连接）又贵又慢；养 20 辆常备车（连接池），用完回停车场（归还），随时发车。

**这个比喻的局限**：连接池里的连接可能因为数据库重启而失效，需要"探活/重建"机制——快递车不会自己报废。

## 第四部分：API 设计与认证

### 4.1 什么是 API？什么是 RESTful API？

**定义**：API（Application Programming Interface，应用程序编程接口）是**两个程序之间约定的通信接口**。网站前后端的 API 就是"前端发什么请求、后端返回什么数据"的一套约定。

**REST（Representational State Transfer，表现层状态转换）**：一种 API 设计风格，核心思想是——**把一切数据看作"资源"，用 HTTP 方法对资源做操作**。

| HTTP 方法 | 含义 | 比喻（餐厅） | 资源操作 |
|-----------|------|------------|---------|
| GET | 读取 | 看菜单 | 查询（不改数据） |
| POST | 创建 | 下单 | 新增资源 |
| PUT | 整体更新 | 换掉整道菜 | 替换 |
| PATCH | 局部更新 | 只换辣度 | 部分修改 |
| DELETE | 删除 | 撤单 | 删除资源 |

**RESTful 设计示例（你的 OJ 项目）**：

| 请求 | 语义 |
|------|------|
| `GET /problems` | 获取题目列表 |
| `GET /problems/42` | 获取 42 号题目详情 |
| `POST /submissions` | 提交一份代码 |
| `GET /submissions?problem_id=42` | 按题目查提交记录 |
| `POST /auth/login` | 登录（认证不是资源，用 POST 动作） |

**设计原则**：**URL 用名词表示资源，不用动词**。`/getProblems` 是反例，`GET /problems` 才对。

### 4.2 HTTP 状态码 —— 后端要主动"告诉结果"

后端返回响应时，必须带上正确的状态码，前端才能判断成功失败。

| 状态码 | 含义 | 比喻 | 常见场景 |
|--------|------|------|---------|
| 200 | OK 成功 | 菜好了 | 查询成功 |
| 201 | Created 已创建 | 下单成功 | POST 创建成功 |
| 400 | Bad Request 请求格式错 | 菜单看不懂你点啥 | 参数缺失、JSON 格式错 |
| 401 | Unauthorized 未认证 | 没验会员卡 | 没带 token / token 过期 |
| 403 | Forbidden 无权限 | 会员卡没权限 | 游客访问管理接口 |
| 404 | Not Found 不存在 | 菜单上没这道菜 | URL 错、资源不存在 |
| 500 | Internal Server Error | 后厨炸了 | 代码异常 |

**最佳实践**：返回 JSON 时统一带上**业务状态码**，方便前端区分：

```python
@app.route('/problems/<int:pid>')
def get_problem(pid):
    problem = Problem.get_or_none(Problem.id == pid)
    if not problem:
        return jsonify({'code': 40401, 'message': '题目不存在'}), 404
    return jsonify({'code': 20000, 'data': {'title': problem.title}})
```

### 4.3 JSON 与请求响应规范

**JSON（JavaScript Object Notation，JavaScript 对象表示法）**：前后端通信的事实标准格式。它长得和 Python 字典几乎一样。

```json
{
  "code": 20000,
  "message": "success",
  "data": {
    "username": "z",
    "role": "manager"
  }
}
```

**统一响应结构建议**（你的项目风格）：

```
{ code: 业务状态码, message: 提示信息, data: 实际数据 }
```

**好处**：前端拿到任何响应都能按统一结构解析；异常时 message 可直接展示给用户。

### 4.4 分页、错误处理与 API 版本（API 实战三件套）

#### ① 分页（Pagination）——列表接口必备

**问题**：`GET /problems` 若有 10 万道题，一次性全返回，响应要几 MB、加载要几秒，还会拖垮服务器。

**解决**：分页返回——一次只给一页。

```python
@app.route('/problems')
def list_problems():
    page = request.args.get('page', default=1, type=int)      # 第几页
    size = request.args.get('size', default=20, type=int)     # 每页几条
    total = Problem.select().count()                          # 总条数
    problems = (Problem
                .select()
                .order_by(Problem.id.desc())
                .paginate(page, size))                        # Peewee 自带分页
    return jsonify({'code': 20000, 'data': {
        'items': [p.title for p in problems],
        'total': total, 'page': page, 'size': size
    }})
```

**比喻**：分页 = **书店按章节卖书**。你不会一次扛走整套《资治通鉴》，而是告诉店员"我要第 3 章到第 4 章"（page=2, size=2）。**最佳实践**：`size` 要设上限（如最大 100），防止有人传 `size=9999999` 绕过分页。

#### ② 全局异常处理——统一兜底

**问题**：代码里没 catch 的异常，Flask 默认返回 500 和一坨 HTML 报错页，前端没法处理。

**解决**：注册**全局错误处理器**，把异常统一转成 JSON。

```python
@app.errorhandler(404)
def not_found(e):
    return jsonify({'code': 40400, 'message': '资源不存在'}), 404

@app.errorhandler(500)
def server_error(e):
    app.logger.exception(e)      # 关键：记录完整堆栈到日志
    return jsonify({'code': 50000, 'message': '服务器开小差了'}), 500
```

**铁律**：**返回给用户的 message 要温和模糊，完整错误只进日志**——否则攻击者能从报错里摸清你的系统结构。

#### ③ API 版本控制

**问题**：接口 v1 上线后被很多客户端在用，v2 要改字段，直接改会搞坏老客户端。

**解决**：URL 里带版本号 `/api/v1/problems`、`/api/v2/problems`，新旧并存，老客户端平滑升级。

**比喻**：软件版本 = **菜谱改版**。老顾客爱旧口味（v1），新顾客用新口味（v2），两版同时供应，等老顾客都吃腻了再下架旧菜。

### 4.5 认证方式：Session vs JWT

网站需要识别"你是谁"。两种主流方案：

| 方案 | 原理 | 比喻 | 优点 | 缺点 |
|------|------|------|------|------|
| Session | 服务端存会话，浏览器存 ID | 餐厅前台存你的记录，你拿号牌 | 可随时撤销 | 占服务端内存、多服务器要共享 |
| **JWT** | 服务端签发带签名的令牌，浏览器保存，服务端验签 | 带防伪章的会员卡 | 无状态、可扩展 | 撤销难、过期前一直有效 |

**JWT（JSON Web Token）结构**——三段由 `.` 连接：

```
eyJhbGciOiJIUzI1NiJ9.eyJ1c2VyX2lkIjoyfQ.Kd9Xm2rQc...
└─ Header(算法) ┘  └─ Payload(数据) ┘  └─ Signature(签名) ┘
```

**三段分别是**：
1. **Header**：声明签名算法（如 HS256）。
2. **Payload**：要带的数据（user_id、role、过期时间 exp）。
3. **Signature**：用密钥对前两段做签名——**防止篡改的关键**。

**为什么能防伪造（原理）**：签名是用**只有服务器知道的密钥**计算的。攻击者改了 Payload，签名就对不上，服务器验签时直接拒绝。**比喻**：会员卡上的防伪章——顾客改不了，只有办卡的店家能盖。

**你的项目里就在用**：登录后生成 JWT，前端存起来，每次请求放在 `Authorization: Bearer <token>` 请求头里发给后端验证；你项目还用 Redis 做 JWT 黑名单（注销后把 token 拉黑）。

### 4.6 CORS（跨域资源共享）—— 浏览器安全机制

**问题**：前端在 `oj.xauat.site`，后端在 `ojapi.xauat.site`，浏览器会拦截跨域的请求。

**为什么拦截**：浏览器出于安全，默认禁止"来自 A 网站的 JS 去读取 B 网站的数据"（防 CSRF 攻击）。

**解决——CORS（Cross-Origin Resource Sharing，跨域资源共享）**：后端在响应头里声明"我允许哪些来源访问"。

**你的项目里就在用**：`ALLOWED_ORIGINS` 配置 + Flask-CORS，就是在响应头里加 `Access-Control-Allow-Origin` 白名单。

**注意**：CORS 是**浏览器**的安全机制，不是服务器的。服务器本身不拒绝跨域请求，是浏览器帮忙拦的。**比喻**：不是餐厅不给外人上菜，而是"送外卖的只认顾客指定的地址"。

### 4.7 认证在 API 中的完整流程

用户登录到访问受保护接口的完整链路：

```
① 前端 POST /auth/login  {username, password}
② 后端校验密码哈希（不存明文密码！）
③ 后端签发 JWT  {user_id, role, exp}
④ 前端保存 token（localStorage 或 Pinia）
⑤ 后续请求带 Authorization: Bearer <token>
⑥ 后端中间件验签：合法→放行；过期/伪造→401
⑦ 需要权限的接口再查 role：manager 才放行
```

**错误处理**：每个环节失败都要返回明确状态码——密码错返回 401；token 过期返回 401（前端收到后跳登录页）；无权限返回 403。

## 第五部分：部署上线

### 5.1 开发环境 vs 生产环境（关键区别）

| 维度 | 开发环境 | 生产环境 |
|------|---------|---------|
| 服务器 | Flask 自带开发服务器 | Gunicorn 等生产级 WSGI 服务器 |
| 调试 | `debug=True`，改代码自动重启 | `debug=False`，禁详细报错 |
| 数据库 | 本地 PostgreSQL | 云数据库或服务器上的 PostgreSQL |
| 密钥 | 随便填 | 环境变量管理，绝不提交 Git |
| 地址 | `localhost` | 域名 + HTTPS |

**铁律**：**生产环境绝不开启 debug 模式**。原因：debug 模式会把完整报错（含代码、路径、甚至敏感信息）显示给访问者，是重大安全隐患。

### 5.2 为什么用 Gunicorn 而不是 Flask 自带服务器

Flask 自带的 `app.run()` 服务器是**单进程、同步**的，一个请求没处理完，其他请求都得排队——生产环境根本扛不住。

**Gunicorn（Green Unicorn）**是生产级 WSGI 服务器，核心能力是**多 Worker**：

```bash
gunicorn -w 4 -b 0.0.0.0:8000 app:app
```

`-w 4` = 启动 4 个 worker 进程，同时处理 4 个请求。`app:app` = 从 `app.py` 里取 `app` 变量。

**比喻**：Flask 自带服务器 = 一个厨师；Gunicorn = 雇了 4 个厨师同时炒菜。

**这个比喻的局限**：多进程有**副作用**——进程间不共享内存。如果你的代码在进程内缓存了数据（比如内存缓存），4 个进程各存各的，会产生数据不一致。

### 5.3 Nginx 反向代理（服务器大门）

**定义**：Nginx 是一个高性能 Web 服务器，常作为**反向代理**站在后端前面。

**反向代理（Reverse Proxy）**：客户端把请求发给 Nginx，Nginx 再转发给真正的后端。

```
用户浏览器 → Nginx(:80/:443) → Gunicorn(:8000) → Flask
```

**为什么需要 Nginx**：

| 职责 | 说明 |
|------|------|
| 静态文件 | 前端打包产物（HTML/CSS/JS）由 Nginx 直接返回，不经过 Flask |
| 反向代理 | 把 API 请求转发给 Gunicorn |
| 负载均衡 | 有多个后端实例时，Nginx 分发给不同实例 |
| HTTPS 终结 | 处理 SSL 证书加解密，后端不用管 |
| 安全防护 | 限制请求体大小、防简单攻击 |

**比喻**：Nginx = 餐厅**迎宾员**。顾客（请求）进门，迎宾员判断：要菜单（静态文件）直接给；要后厨做菜（API）就送到对应厨师（Gunicorn）。

**简单 Nginx 配置示例**：

```nginx
server {
    listen 80;
    server_name oj.xauat.site;

    # 前端静态文件
    location / {
        root /var/www/oj-frontend/dist;
        try_files $uri /index.html;   # SPA 路由回退
    }

    # API 转发给后端
    location /api/ {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
    }
}
```

### 5.4 HTTPS 与证书（把数据锁进保险箱）

**问题**：上面 Nginx 用的是 `listen 80`（HTTP 明文）。用户在浏览器输入的密码、token，经过网络传输时**裸奔**——中间的任何节点（路由器、公共 WiFi、运营商）都能看到内容。

**HTTPS（HyperText Transfer Protocol Secure）** = HTTP + TLS 加密。浏览器与服务器先握手协商密钥，之后所有数据加密传输。

**核心原理——TLS 握手**（极简版）：
```
① 浏览器 → 服务器：你好，我想加密通信
② 服务器 → 浏览器：这是我的数字证书（含公钥，由 CA 签名）
③ 浏览器验证证书 → 用公钥加密一个"会话密钥"发给服务器
④ 服务器用私钥解开 → 之后双方用会话密钥加密通信
```

**证书与 CA**：数字证书由 **CA（Certificate Authority，证书颁发机构）** 签发，证明"这个公钥确实属于 oj.xauat.site"。浏览器内置了可信 CA 名单，验证通过才继续。**比喻**：证书 = 公章的**真伪验证**——快递员亮出营业执照（证书），顾客查工商系统（CA）确认是真店，才敢把货（数据）交给他。

**部署实操**：用 **Let's Encrypt + Certbot** 可以免费申请证书，一条命令自动配置 Nginx：
```bash
sudo certbot --nginx -d oj.xauat.site
```
之后 `listen 80` 会自动加 `return 301 https://...` 跳转，`listen 443 ssl` 承载加密流量。

**比喻**：HTTP = 透明信封；HTTPS = 上了锁的保险信封。锁是公钥，只有收件人的私钥能开——中途有人拿到信也打不开。

### 5.5 环境变量管理配置与密钥

**问题**：数据库密码、JWT 密钥、API Key 不能写死在代码里（会被提交进 Git 泄露）。

**解决**：用**环境变量**或 `.env` 文件存敏感配置。

```bash
# .env 文件（加入 .gitignore，绝不提交）
DB_HOST=localhost
DB_PASSWORD=super_secret
JWT_SECRET_KEY=very_long_random_string
ALLOWED_ORIGINS=https://oj.xauat.site
```

```python
import os
DB_PASSWORD = os.getenv('DB_PASSWORD')
```

**比喻**：代码 = 公开的菜谱；密钥 = 保险柜密码。菜谱可以给所有人看，保险柜密码只能你一个人知道，而且不能写在菜谱上。

### 5.6 日志与监控（出了事要能查）

生产环境出了问题，你靠什么定位？**日志**。

| 日志级别 | 含义 | 比喻 |
|---------|------|------|
| DEBUG | 调试细节 | 厨师自言自语 |
| INFO | 正常运行记录 | 每道菜的出餐记录 |
| WARNING | 可能有隐患 | 灶台有点漏气 |
| ERROR | 出错但仍运行 | 这道菜做砸了 |
| CRITICAL | 严重故障 | 后厨着火 |

**最佳实践**：
- 记录请求方法、URL、状态码、耗时。
- 不记录密码、token 等敏感信息。
- 日志带时间戳和 trace ID（便于串起一次请求的全部日志）。
- 监控 CPU、内存、数据库连接数，超阈值告警。

**比喻**：日志 = 后厨的**摄像头 + 台账**。平时不显眼，出事后靠它复盘"哪一步出了问题"。

### 5.7 CI/CD（自动化部署流程）

**CI（Continuous Integration，持续集成）**：代码一提交就自动构建 + 跑测试。
**CD（Continuous Delivery/Deployment，持续交付/部署）**：测试通过后自动部署上线。

**比喻**：CI/CD = 工厂的**自动化流水线**——原料（代码）进来，自动质检（测试）、自动包装（构建）、自动发货（部署），全程不用人盯。

**你的项目的部署流程（手动版）**：

```
本地 push → 服务器 git pull → 重启 Gunicorn → 前端 Vite build → Nginx 托管
```

升级为 CI/CD 后，push 到特定分支会自动完成以上所有步骤。

## 第六部分：常见误区

### 6.1 误区一：后端 = 只会拼 SQL / 只会写接口

后端不只是"查数据返回"。真正的后端要负责：**安全**（防注入、防越权）、**性能**（索引、缓存、分页）、**稳定性**（异常处理、日志、限流）、**设计**（分层、可测试、可扩展）。

### 6.2 误区二：把用户输入直接拼进 SQL

```python
# ❌ 致命错误：SQL 注入漏洞
sql = f"SELECT * FROM users WHERE username='{username}'"
# 攻击者输入：' OR '1'='1
# 实际拼成的 SQL：SELECT * FROM users WHERE username='' OR '1'='1'
#                                    ↑ 引号闭合后，后面的 OR 恒为真 → 查出全部用户！
```

**正确做法**：永远用 ORM 参数化查询（Peewee 天然防住）。

### 6.3 误区三：密码明文存储

**绝对禁止**把用户密码明文存数据库。正确做法：存**哈希值**（如 bcrypt），校验时只比哈希。

```python
from werkzeug.security import generate_password_hash, check_password_hash

stored = generate_password_hash(password)   # 存库
check_password_hash(stored, password_input) # 校验
```

**比喻**：密码 = 存的是"打码后的指纹"，不是指纹原样。即使数据库泄露，攻击者也无法直接得知明文密码。

### 6.4 误区四：N+1 查询（性能杀手）

**问题**：查 100 个用户，却发起了 101 次查询（1 次查列表 + 100 次查每个人的订单）。

**比喻**：取 100 份快递，每份都跑一趟仓库，而不是一趟搬回来。

**解决**：用 JOIN 或 ORM 预加载（`select_related` / `prefetch_related`）。

### 6.5 误区五：错误处理只 try 不处理

```python
# ❌ 静默吞掉异常，出问题毫无痕迹
try:
    result = do_something()
except Exception:
    pass

# ✅ 记日志 + 返回明确错误
try:
    result = do_something()
except Exception as e:
    app.logger.error(f"操作失败: {e}")
    return jsonify({'code': 50001, 'message': '服务器内部错误'}), 500
```

**铁律**：**异常可以吞，但必须留痕**（日志）。否则线上出问题你连从哪排查都不知道。

### 6.6 误区六：所有东西都塞进一张表 / 一个函数

- 数据：违背**范式**设计（重复存储、更新异常）。
- 代码：违背**分层**，2000 行一个函数，无法维护、无法测试。

### 6.7 误区七：只防 SQL 注入，不防 XSS 和 CSRF

Web 安全三大经典攻击，SQL 注入只是其一：

| 攻击 | 原理 | 比喻 | 防御 |
|------|------|------|------|
| **SQL 注入** | 用户输入拼进 SQL 被执行 | 点菜时顺便下达"后厨指令" | 参数化查询（ORM） |
| **XSS 跨站脚本** | 用户输入含 `<script>` 被浏览器当代码执行，可偷 Cookie/令牌 | 顾客在菜单留言栏里夹了"魔法纸条"，服务员把纸条当指令执行了 | 输出转义（前端 `v-html` 慎用 + 后端转义） |
| **CSRF 跨站请求伪造** | 用户已登录 A 站，被恶意 B 站页面诱导发请求，浏览器自动带上 A 站 Cookie | 有人借你的会员卡进店消费，店家以为是你在点单 | JWT 放 Header（你的方案天然防）、`SameSite` Cookie、CSRF Token |

**你的项目为什么相对安全**：JWT 放在 `Authorization` 请求头而非 Cookie——CSRF 攻击靠"浏览器自动带 Cookie"，请求头不会被自动带上，所以 JWT+Header 方案天然防 CSRF。XSS 则要靠前端不渲染用户输入为 HTML 来防。

> **思考题 6**：一个用户提交了 100 道题的代码，你查"这个用户所有提交"时误用了 N+1 查询，实际发出了多少次数据库查询？

## 附录 A：思考题参考答案

**思考题 1**：Nginx 充当反向代理和静态文件服务器。它直接返回前端静态文件（不占 Flask 资源），转发 API 请求给 Gunicorn，同时负责 HTTPS、负载均衡、安全防护。Flask 只专注处理业务请求，职责更清晰、更安全。

**思考题 2**：Controller 直接写数据库查询会导致：①职责混乱，业务逻辑和请求处理耦合，代码难维护；②难测试（测 Controller 还要连数据库）；③难复用（同一个查询逻辑无法被多个接口共用）。正确做法是 Controller 只调 Service，Service 调 Model。

**思考题 3**：索引加速查询的原理是走 B+ 树查找（O(log n)）而非全表扫描（O(n)）。但索引会占磁盘空间，且每次 INSERT/UPDATE/DELETE 都要同步维护索引，写操作变慢。所以只给高频查询字段建索引，别给低选择性字段（如性别）建。

**思考题 4**：如果 JWT 还没过期，服务器**无法仅凭令牌本身发现**它被偷——JWT 是无状态的，服务器只验签和看过期时间。签名有效 + 未过期 = 通过。这是 JWT 的核心局限。缓解手段：缩短过期时间、用 Redis 黑名单（你项目已在做）、检测异常 IP 等。

**思考题 5**：`debug=True` 会把**完整的报错堆栈、源码片段、配置信息**显示给任何访问者。攻击者可借此获取代码结构、路径、数据库连接信息甚至密钥，从而发起精准攻击。这是生产环境的重大安全漏洞，必须 `debug=False`。

**思考题 6**：101 次。1 次查"该用户的提交列表" + 100 次查每条提交关联的其他数据（如题目信息）= 101 次查询。数据量越大浪费越严重，这就是 N+1 查询问题的本质。
