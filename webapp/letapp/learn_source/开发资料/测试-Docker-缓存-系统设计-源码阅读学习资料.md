## 第一部分：软件测试

### 1.1 什么是测试？为什么要写测试？

**定义**：软件测试是**编写代码来验证另一段代码行为是否符合预期**。

**为什么不手动测**：手点界面验证太慢、容易漏、改一次测一次累死人。自动化测试**写一次，每次改动自动跑**。

| 痛点 | 没有自动化测试 | 有自动化测试 |
|------|--------------|-------------|
| 改代码 | 生怕改坏其他功能，全靠胆量 | 一键跑全部测试，坏了立刻知道 |
| 重构 | 不敢动，一动就出 bug | 测试兜底，放心重构 |
| 团队协作 | 谁改了都不知道坏了什么 | CI 自动拦截错误提交 |
| 上线 | 心里没底 | 测试全绿才敢发 |

**比喻**：测试 = **质检流水线**。每道菜（每次提交的代码）出锅前先过质检，不合格打回重做，合格才端给顾客（上线）。

### 1.2 测试金字塔（测试的层次结构）

好的测试体系是**金字塔**形状——底层多、上层少：

```
        /  E2E 端到端测试  \     ← 少而慢，测完整用户流程
       /   集成测试        \      ← 中等，测模块配合
      /_____________________\    ← 多而快，测单个函数
        单元测试（数量最多）
```

| 层 | 测什么 | 特点 | 例子 |
|----|--------|------|------|
| 单元测试 | 单个函数/类 | 快、多、隔离 | 测 `calculate_score()` 算法 |
| 集成测试 | 模块间配合 | 中等 | 测"Service 调 Model + 数据库" |
| 端到端 E2E | 完整用户流程 | 慢、少 | 测"注册→登录→做题→提交" |

**比喻**：单元测试 = 检查每个零件；集成测试 = 检查零件组装起来能否运转；E2E = 整辆车试驾。

**这个比喻的局限**：金字塔不是死的。有的公司因 UI 变化频繁反而 E2E 少、API 集成测试多——原则是"**层越低越该多、越稳越快**"。

### 1.3 pytest 单元测试入门（你的项目用 pytest）

**pytest 是 Python 最主流的测试框架**。三个核心规则：
1. 测试文件以 `test_` 开头（如 `test_score.py`）。
2. 测试函数以 `test_` 开头。
3. 用 `assert` 断言（pytest 会自动展示断言失败详情）。

```python
# score.py（被测代码）
def calculate_score(correct: int, total: int) -> float:
    if total == 0:
        return 0.0
    return round(correct / total * 100, 2)

# test_score.py（测试代码）
from score import calculate_score

def test_all_correct():
    assert calculate_score(10, 10) == 100.0

def test_half_correct():
    assert calculate_score(5, 10) == 50.0

def test_zero_total():
    assert calculate_score(0, 0) == 0.0

def test_partial():
    assert calculate_score(3, 4) == 75.0
```

运行：终端执行 `pytest -v`，会看到 4 个测试全部 PASS。

**pytest 常用特性**：

| 特性 | 作用 | 示例 |
|------|------|------|
| `-v` | 显示详细输出 | `pytest -v` |
| `-k` | 按名字筛选测试 | `pytest -k "zero"` |
| fixture | 测试前准备数据/环境 | 见下 |
| parametrize | 一组参数跑多个用例 | `@pytest.mark.parametrize("a,b", [(1,2),(3,4)])` |
| monkeypatch | 替换函数/环境变量 | 见下 |

**测试覆盖率（coverage）**——测了多少代码：

```bash
pip install pytest-cov
pytest --cov=score --cov-report=term-missing
```

输出会显示**每行代码被执行过没有**（未覆盖的行标 `Missing`）。**注意**：覆盖率是"代码被执行了多少"，**不等于"行为是否正确"**——详见第六部分误区一。

### 1.4 Fixture（测试的"摆台"）

**定义**：fixture 是**测试运行前自动准备、测试结束后自动清理**的东西——比如造一个测试数据库、准备一份测试数据。

```python
import pytest

@pytest.fixture
def sample_user():
    return {"id": 1, "username": "alice", "role": "manager"}

def test_user_role(sample_user):
    assert sample_user["role"] == "manager"
```

**fixture 的威力——作用域**：`@pytest.fixture(scope="function")` 每个测试都重建；`scope="session"` 整个测试会话只建一次。**比喻**：function 级 = 每桌客人现摆餐具；session 级 = 宴会厅一次布置好，多场共用。

### 1.5 Monkeypatch 与 Mock（隔离外部依赖）

**问题**：被测函数里调用 Redis、PostgreSQL、外部 API，测试时不能真连（慢、不稳定、还可能花钱）。

**解决**：用 monkeypatch/mock **把真实依赖替换成假实现**。

```python
# cache_module.py（被测模块）——真实运行时会连 Redis 和数据库
import redis
from mydb import find_announcement   # 真实数据库查询

def get_announcement(ann_id):
    cache = redis.Redis()
    data = cache.get(f"announcement:{ann_id}")
    if data:
        return data
    data = find_announcement(ann_id)      # 查数据库
    cache.set(f"announcement:{ann_id}", data)
    return data

# test_cache_module.py（测试）——用 monkeypatch 把 redis 和 find_announcement 换成假的
import cache_module

def test_cache_hit(monkeypatch):
    # 1) 用 monkeypatch 替换 redis.Redis：不让测试真的连 Redis
    class FakeRedis:
        def get(self, key):    return "缓存里的数据"
        def set(self, key, v): pass
    monkeypatch.setattr("redis.Redis", FakeRedis)

    # 2) 用 monkeypatch 替换数据库查询函数：记录是否被调用
    calls = []
    monkeypatch.setattr(cache_module, "find_announcement", lambda ann_id: calls.append(ann_id) or "数据库里的数据")

    assert cache_module.get_announcement(1) == "缓存里的数据"
    assert calls == []        # 命中缓存，数据库函数未被调用 → 证明走了缓存
```

**比喻**：Mock = **拍戏的替身/道具**。测试不需要真的开一家银行（真数据库），用假银行（Mock）就够了——重点是验证"演员（你的函数）的台词对不对"。

**这个比喻的局限**：Mock 太假会有风险——**假实现和真实行为不一致**，导致测试全绿但上线出错。所以 Mock 只隔离**自己不关心的外部依赖**，核心逻辑尽量用真数据测。

### 1.6 TDD（测试驱动开发）

**定义**：TDD（Test-Driven Development，测试驱动开发）是**先写测试、再写代码、最后重构**的开发方式。

**三步骤循环（Red-Green-Refactor）**：

```
① RED：先写测试 → 运行 → 测试失败（因为代码还没写）
② GREEN：写最少代码让测试通过 → 运行 → 测试变绿
③ REFACTOR：重构代码 → 运行 → 依然全绿
```

```python
# 步骤①：先写测试
def test_add():
    assert add(2, 3) == 5   # add 还没实现，运行会报 NameError → RED

# 步骤②：写代码让它通过
def add(a, b):
    return a + b            # 运行 → 通过 → GREEN
```

**好处**：
- 逼你先想清楚"输入→输出"的契约。
- 代码覆盖率天然高（每个功能都有测试）。
- 重构有安全网。

**比喻**：TDD = **先画靶子再射箭**。先明确"射中哪里算赢"（测试），再去射（写代码），而不是射完再画圈。

### 1.7 集成测试与 E2E 测试

**集成测试**（你的项目下一步重点）：验证模块配合，特别是"Service → Model → 真实数据库"链路。

```python
# test_announcement_api.py —— 给公告接口写集成测试
from app import app

def test_create_announcement():
    client = app.test_client()
    resp = client.post('/announcements', json={
        'title': '比赛开始',
        'content': '今晚 8 点第一场'
    })
    assert resp.status_code == 201
    assert resp.get_json()['data']['title'] == '比赛开始'
```

**E2E（End-to-End，端到端）测试**：用浏览器自动化模拟真实用户操作。工具如 **Selenium、Playwright**。

```python
# Playwright 示例（伪代码示意）
from playwright.sync_api import sync_playwright

with sync_playwright() as p:
    browser = p.chromium.launch()
    page = browser.new_page()
    page.goto("https://oj.xauat.site")
    page.fill("#username", "alice")
    page.fill("#password", "***")
    page.click("#login-btn")
    page.wait_for_selector(".welcome")
    assert "欢迎" in page.inner_text(".welcome")
```

## 第二部分：Docker

### 2.1 为什么需要 Docker？它解决了什么？

**痛点**：你的代码依赖特定 Python 版本、特定 PostgreSQL 版本、特定系统库。换一台电脑/服务器，环境不一样，项目就跑不起来——"在我电脑上是好的"这句话成了经典笑话。

**Docker 解决**：把**代码 + 运行环境 + 依赖**整体打包成一个可移植的"集装箱"（镜像），在任何装有 Docker 的机器上一键运行，结果完全一致。

| 痛点 | 没有 Docker | 有 Docker |
|------|-----------|----------|
| 环境不一致 | "在我电脑上是好的" | 镜像里环境固定，处处一致 |
| 部署繁琐 | 手动装 Python/库/数据库 | 一条命令启动整套 |
| 多服务编排 | 手动一个个启动 | docker-compose 一键全起 |
| 资源隔离 | 依赖冲突、端口打架 | 每个容器独立隔离 |

**比喻**：Docker = **集装箱**。不管里面装的是衣服还是电器（什么应用），集装箱尺寸统一、装卸标准统一，从上海到纽约（任何机器）都能直接搬运，不用重新包装。

### 2.2 镜像 vs 容器（最重要的一对概念）

| 概念 | 是什么 | 比喻 | 类比对象 |
|------|--------|------|---------|
| **镜像（Image）** | 只读的打包模板 | 集装箱的"设计图/模具" | 类（Class） |
| **容器（Container）** | 镜像运行起来的实例 | 一个正在运输的集装箱 | 对象（Instance） |

**镜像可以理解成"模板"**：一个镜像可以启动多个容器，彼此独立互不影响。

**比喻展开**：镜像 = **装好货的集装箱**（固定内容）；容器 = **这个集装箱在船上的一个位置**。你可以把一个镜像的货物复制成两份，装上两条不同的船（启动两个容器）。

**这个比喻的局限**：容器不是完全隔离的"另一个电脑"——它们**共享宿主机的操作系统内核**，只是逻辑上隔离了文件系统、进程、网络。所以 Docker 比虚拟机轻量得多（见 2.6）。

### 2.3 Dockerfile（集装箱的"装箱单"）

**Dockerfile** 是描述"如何构建镜像"的文本文件。

```dockerfile
# 基于 Python 3.11 官方镜像
FROM python:3.11-slim

# 设置工作目录
WORKDIR /app

# 先复制依赖清单（利用层缓存加速）
COPY requirements.txt .
RUN pip install -r requirements.txt

# 复制项目代码
COPY . .

# 暴露端口
EXPOSE 8000

# 启动命令
CMD ["gunicorn", "-w", "4", "-b", "0.0.0.0:8000", "app:app"]
```

**Dockerfile 常用指令**：

| 指令 | 作用 | 比喻 |
|------|------|------|
| FROM | 基于哪个基础镜像 | 用哪块地基开始盖 |
| COPY | 把文件复制进镜像 | 往集装箱里装货 |
| RUN | 构建时执行命令 | 装箱时组装 |
| WORKDIR | 设置工作目录 | 干活的工作台 |
| EXPOSE | 声明容器监听端口 | 集装箱上的通气口说明 |
| CMD | 容器启动时执行命令 | 集装箱到站后执行的卸货程序 |

**关键原理——分层缓存**：Docker 镜像由**一层层**组成，每层对应一条 Dockerfile 指令。构建时，**没变的层直接复用缓存**，只有变了的层才重建。所以把 `COPY requirements.txt` 放在 `COPY . .` 前面——依赖没变时，pip install 那层就不用重跑，构建飞快。

#### Dockerfile 的两个进阶实践

**① `.dockerignore`（和 `.gitignore` 一样重要）**：指定哪些文件**不**被 COPY 进镜像。没有它，`COPY . .` 会把 `venv/`、`.git/`、`node_modules/`、`.env`（含密钥！）全部打包进镜像——镜像巨大还泄露密钥。

```
# .dockerignore
venv/
__pycache__/
.git/
.env
node_modules/
```

**② 用非 root 用户运行**：容器默认以 root 身份运行，一旦容器被攻破，攻击者拿到的是宿主机的最高权限。**最佳实践**：在镜像里创建一个普通用户并用它运行。

```dockerfile
RUN useradd -m appuser
USER appuser          # 之后的 CMD 都以普通用户身份跑
```

**比喻**：普通用户运行 = 保洁阿姨只有**自己房间的钥匙**（自己的应用目录），就算房间被翻，也开不了整栋楼的配电房（宿主机系统）。

### 2.4 常用 Docker 命令

| 命令 | 作用 | 说明 |
|------|------|------|
| `docker build -t my-app .` | 用 Dockerfile 构建镜像 | `-t` 起名字 |
| `docker images` | 查看本地镜像列表 | — |
| `docker run -p 8000:8000 my-app` | 运行容器 | `-p 宿主机:容器` 端口映射 |
| `docker ps` | 查看运行中的容器 | 加 `-a` 看所有 |
| `docker stop <id>` | 停止容器 | — |
| `docker rm <id>` | 删除容器 | — |
| `docker exec -it <id> bash` | 进入容器内部 | 调试用 |
| `docker logs <id>` | 查看容器日志 | 排错第一手段 |

**端口映射原理**：容器有自己独立的网络。`-p 8000:8000` 表示"把宿主机的 8000 端口收到的请求转发到容器里的 8000 端口"。**比喻**：集装箱在码头有编号，`-p` 就是在码头门口立牌子："去 3 号集装箱的货请从这道门进"。

### 2.5 Docker Compose（多容器一键编排）

**问题**：你的 OJ 项目需要 PostgreSQL + Redis + 后端 + 前端 四个服务，用 docker run 一个个起太麻烦，且要手动配置它们之间的网络连接。

**解决**：docker-compose.yml 一个文件描述全部服务，`docker compose up -d` 一键全起。

```yaml
# 注意：新版 docker compose（v2）已不需要 version 字段，写 version 会报警告但不影响运行
services:
  db:
    image: postgres:16
    environment:
      POSTGRES_USER: oj
      POSTGRES_PASSWORD: secret
      POSTGRES_DB: ojdb
    volumes:
      - pgdata:/var/lib/postgresql/data

  redis:
    image: redis:7

  backend:
    build: ./backend
    environment:
      DB_HOST: db          # compose 里用服务名互相访问
      REDIS_HOST: redis
    depends_on:
      - db
      - redis
    ports:
      - "8000:8000"

  frontend:
    build: ./frontend
    ports:
      - "80:80"

volumes:
  pgdata:
```

**关键点**：compose 会自动创建内部网络，服务之间用**服务名**（`db`、`redis`）当主机名互相访问，不用写 IP。`depends_on` 保证启动顺序。文件顶部**不写 `version` 字段**是 Compose v2 的推荐写法（写旧版 `version: "3.x"` 只是过时，不报错）。

**为什么必须有 volumes（数据持久化）**：容器被删除后，容器内的文件**全部消失**。如果你把 PostgreSQL 数据存在容器里，`docker compose down` 一次数据就没了。上面配置里 `pgdata:/var/lib/postgresql/data` 就是把数据库文件挂到宿主机——**容器死了，数据还活着**。

**比喻**：容器 = 临时工，干完活就走；volume = 公司**档案柜**（在宿主机上）——临时工走了，档案柜里的文件（数据）原封不动。

**这个比喻的局限**：volume 里的数据仍在宿主机磁盘上，宿主机磁盘坏了照样丢——所以生产环境还要给数据库做**定期备份**（导出 SQL / 快照）。

### 2.6 容器 vs 虚拟机（关键辨析）

很多人以为容器就是虚拟机，其实完全不同：

| 维度 | 虚拟机（VM） | 容器（Docker） |
|------|-------------|---------------|
| 隔离级别 | 虚拟化整个硬件，每个 VM 有完整操作系统 | 共享宿主机内核，只隔离进程/文件/网络 |
| 启动速度 | 分钟级 | 秒级 |
| 体积 | GB 级 | MB 级 |
| 资源占用 | 每个 VM 吃一套 OS 开销 | 轻量，接近原生进程 |
| 隔离强度 | 强（完全独立） | 较弱（共享内核，有逃逸风险） |

**比喻**：虚拟机 = 每人租一整套房（有独立厨房卫生间）；容器 = 合租房（共享水电管道，但各住各的房间）。

**这个比喻的局限**：合租的"共享管道"意味着一个容器恶意攻击可能影响宿主机——所以 Docker 有"最小权限"、非 root 运行等安全最佳实践，虚拟机隔离则天然更硬。

### 2.7 Docker Hub 与镜像仓库

**Docker Hub** 是官方的公共镜像仓库，里面存着海量现成镜像（`python`、`postgres`、`redis`、`nginx` 等）。`docker run postgres:16` 时，本地没有会自动从 Docker Hub 拉取。

**比喻**：Docker Hub = **集装箱堆场/建材市场**——常用集装箱（镜像）都有现成的，拖回来直接用，不用自己造。

## 第三部分：缓存（Redis）

### 3.1 为什么需要缓存？速度差在哪？

**核心事实**：内存读取比磁盘读取快约 **100~1000 倍**。

| 存储位置 | 典型耗时 | 比喻 |
|---------|---------|------|
| CPU 缓存 | ~1ns | 脑子里记得 |
| **Redis（内存）** | **~0.1ms** | **书桌桌面上** |
| SSD 磁盘 | ~0.1~1ms | 书架上 |
| 机械硬盘 | ~10ms | 仓库里 |

**问题**：每次请求都查 PostgreSQL（磁盘），QPS 一高数据库就扛不住。

**解决**：把**热点数据**（如公告、题目列表）提前放进 Redis（内存），读取时先查 Redis，命中就不碰数据库。

**比喻**：缓存 = **书桌桌面**。常用的书放桌面上随手就拿（毫秒级）；不常用的收进书架（数据库）。桌面就这么大，所以要放"最常用"的书。

### 3.2 缓存的两个角色：本地缓存 vs 分布式缓存

| 类型 | 例子 | 存在哪 | 优点 | 缺点 |
|------|------|--------|------|------|
| 本地缓存 | Python dict、进程内存 | 每个进程自己 | 极快、无网络开销 | 多进程/多机器数据不一致 |
| 分布式缓存 | **Redis** | 独立服务器 | 多进程/多机器共享 | 有网络开销（仍远快于磁盘） |

**你的项目为什么用 Redis**：Gunicorn 多 worker（多进程），若用本地内存缓存，每个进程各存一份，改公告后有的进程还是旧数据。Redis 是**所有进程共享的同一个缓存**，写入即全员一致。

**比喻**：本地缓存 = 每个人自己的便签；Redis = 办公室**公共白板**——谁都能看、谁都能改、大家看到的是同一份。

### 3.3 Redis 核心数据结构

Redis 不只"存字符串"，它提供多种数据结构：

| 结构 | 例子 | 比喻 | 用途 |
|------|------|------|------|
| String 字符串 | `"alice"` | 一个字条 | 缓存、计数、验证码 |
| Hash 哈希 | `{"username":"alice","role":"manager"}` | 一张登记卡 | 存对象字段 |
| List 列表 | `[a, b, c]` | 一条队伍 | 消息队列、最新列表 |
| Set 集合 | `{a, b, c}`（去重） | 一台集章机 | 去重、好友关系、点赞 |
| ZSet 有序集合 | `{a:100, b:90}` | 带分数的排行榜 | **排行榜**（你的 OJ 排名） |

**Redis 常用命令**（你在 redis常用指令.md 里也有）：

```
SET announcement:1 "今晚8点比赛" EX 60    # 存字符串，60 秒过期
GET announcement:1                      # 取
INCR counter                            # 自增（限流计数）
LPUSH queue "task1"                     # 列表左侧入队
RPOP queue                              # 列表右侧出队（FIFO）
```

**TTL（Time To Live，生存时间）**：给 key 设置过期时间，到期自动删除。`EX 60` = 60 秒后失效。**比喻**：便利贴会过期——写"今晚 8 点"的便利贴，明早就该撕掉。

### 3.4 缓存策略：Cache-Aside（旁路缓存）

最常见且你项目在用的模式。**读**和**写**分别处理：

**读流程（Read）**：
```
① 先查 Redis
② 命中 → 直接返回（快）
③ 未命中 → 查数据库 → 回填 Redis → 返回
```

**写流程（Write）**：先更新数据库，再删掉（或更新）缓存。

**为什么"先写库再删缓存"而不是"先更新缓存"**：若先更新缓存后写库，写库失败时缓存已是新值、库还是旧值，下次读到错误数据。先写库再删缓存，即使删缓存失败，顶多多一次缓存未命中重新查库，不会读到脏数据。

```python
def update_announcement(db, cache, ann_id, new_content):
    # ① 先更新数据库
    db.update(id=ann_id, content=new_content)
    # ② 再删除缓存（下次读时自动回填新值）
    cache.delete(f"announcement:{ann_id}")
```

**比喻**：Cache-Aside = 食堂的**售餐窗口**。先看窗口（缓存）有没有现成的，没有才去后厨（数据库）做并端上窗口（回填）。菜谱改了（数据库更新），就把窗口的旧菜撤走（删缓存）。

#### 四种缓存策略对比（Cache-Aside 只是其中一种）

| 策略 | 谁负责读库 | 谁负责写库 | 优点 | 缺点 | 适合场景 |
|------|-----------|-----------|------|------|---------|
| **Cache-Aside** | 应用自己 | 应用自己 | 灵活、可控、最简单 | 应用要写逻辑 | **你项目在用（读多写少）** |
| **Read-Through** | 缓存层 | 应用 | 读逻辑统一 | 依赖缓存框架 | 框架帮你查库回填 |
| **Write-Through** | 缓存层 | 缓存层 | 读和写都同步，数据最可靠 | 写一次要写两处，慢 | 一致性要求高的写 |
| **Write-Back** | 缓存层 | 缓存层（异步） | 写超快（只写缓存） | 缓存崩了可能丢数据 | 可容忍短暂丢失、写密集 |

**结论**：你项目读多写少 + 可接受短暂不一致 → Cache-Aside 最合适，**不要为了"高大上"引入 Write-Back**。

### 3.5 缓存的三大难题：穿透、击穿、雪崩（重点）

这是 Redis 面试必考、实战必踩的三座山。用一个"查询公告详情"的场景讲解：

| 问题 | 场景 | 后果 | 比喻 |
|------|------|------|------|
| **缓存穿透** | 查一个**根本不存在**的 id（如恶意攻击狂刷不存在的 id） | 缓存永远命中不了，每次都打数据库，数据库被打垮 | 每天有人来问"这道菜有吗？"其实菜单上根本没有，每次都去仓库翻一遍 |
| **缓存击穿** | **某个热点 key** 恰好过期，同时大量请求涌入 | 一个 key 的请求全部打到数据库 | 招牌菜售罄的瞬间，所有顾客同时挤去后厨催单 |
| **缓存雪崩** | **大量 key 同时过期**（如设置了相同过期时间） | 数据库瞬间承受所有请求压力，可能宕机 | 食堂 12:00 所有窗口同时换菜，瞬间挤爆 |

**解决方案**：

| 问题 | 解决方案 | 原理 |
|------|---------|------|
| 穿透 | ① 缓存空值（查询不存在也缓存一个空结果）② 布隆过滤器 | 让"不存在"也命中缓存，不再打库 |
| 击穿 | ① 热点数据不过期（加逻辑过期）② 互斥锁（Mutex），只让一个请求去重建缓存 | 防止所有请求同时打库 |
| 雪崩 | ① 过期时间加随机值（如 60+random(0,30)）② 多级缓存 ③ 服务降级 | 错开过期时间，避免同时失效 |

**布隆过滤器（Bloom Filter）展开**——为什么它能防穿透？

**原理**：用一个超长的二进制位数组 + 几个哈希函数。存 key 时，用 k 个哈希函数算出 k 个位置，全部置 1。查询时算同样 k 个位置，**只要有一个位置是 0，就确定"不存在"**；全部是 1 才可能"存在"。

```
存 "problem:999999" → 哈希函数把第 3、17、80 位置 1
查 "problem:888888" → 3、17、80 处有任一为 0 → 确定不存在 → 直接拒绝，不打数据库
```

**优点**：极省内存（1 亿个 key、误判率约 1% 时，位数组仅约 120MB，且每次查询只有 k 次哈希）。
**缺点（关键局限）**：**只能判断"一定不存在"，无法判断"一定存在"**（不同 key 可能把同一位都置 1，产生误判）。所以布隆过滤器常配合缓存空值一起用：布隆过滤器拦截"一定不存在"的，剩下的交给缓存空值兜底。

**比喻**：布隆过滤器 = 小区门口保安的**大头像册**。保安只认"这栋楼有没有这个人"（在不在），问他"这个人住几零几"他答不上来——他记忆里只有模糊的轮廓（位图），没有精确信息（数据）。

```python
# 穿透解决：缓存空值
def get_announcement(cache, db, ann_id):
    cached = cache.get(f"announcement:{ann_id}")
    if cached is not None:
        return None if cached == "NULL" else cached
    data = db.find(id=ann_id)
    cache.set(f"announcement:{ann_id}", data if data else "NULL", ex=60)
    return data
```

### 3.6 缓存一致性（Cache 与数据库怎么对齐）

**问题**：数据库和缓存是两份数据，更新时如何保证用户看到的不是旧数据？

**核心结论（先记三句）**：
1. **强一致很难且贵**，大部分业务接受"最终一致"。
2. 经典方案：**Cache-Aside**（先更新库，再删缓存）。
3. 极端情况（删缓存失败）：用**延迟双删**或**消息队列补偿**。

**延迟双删**（保底方案）：
```
① 先删缓存
② 更新数据库
③ 等几百毫秒（让可能读旧值的请求写完回填）
④ 再删一次缓存
```

**比喻**：缓存一致性 = **黑板和练习本对账**。理想是每次都对齐；但对不齐的瞬间，顶多晚一点再对齐（最终一致），大多数场景可接受。**涉及钱的系统才需要强一致**。

### 3.7 缓存应用场景汇总（你的项目）

| 场景 | 数据 | 过期策略 |
|------|------|---------|
| 公告列表 | `announcement:*` | 60s + 写操作时失效 |
| JWT 黑名单 | `blacklist:<token>` | 随 token 过期时间 |
| 登录限流 | `ratelimit:<user_ip>` | 窗口期内过期 |
| 排行榜 | ZSet `ranking` | 定期重建 |
| 判题状态轮询 | 提交状态缓存 | 短 TTL |

#### 限流（Rate Limiting）—— Redis 的经典应用

**目的**：限制某个用户/IP 在单位时间内的请求次数，防止脚本刷爆接口或暴力破解登录。

**三种常见算法**：

| 算法 | 做法 | 优点 | 缺点 | 比喻 |
|------|------|------|------|------|
| **固定窗口** | 每分钟计一次数，窗口结束清零 | 简单（一个 INCR + 过期即可） | 窗口边界可能突然涌进双倍流量 | 每分钟记一次人数，但整点瞬间可能挤爆 |
| **滑动窗口** | 用 ZSet 记录每次请求时间戳，只统计最近 N 秒内 | 更平滑 | 内存开销大（每个请求一条记录） | 只看"最近 1 分钟内"来过几个人 |
| **令牌桶** | 匀速往桶里放令牌，有令牌才放行 | 允许短时突发流量 | 实现稍复杂 | 加油站每秒钟补 1 升油，加油可以一次加满 |

**你的项目里就用固定窗口**：Redis 键 `ratelimit:<user_ip>` + `INCR` 计数 + 设置过期时间（窗口长度）。这也是你项目 `middleware/` 中限流中间件的实现。

## 第四部分：系统设计

### 4.1 什么是系统设计？

**定义**：系统设计是**在给定需求下，规划系统的架构**：哪些组件、怎么分工、怎么扩展、怎么保证可用——本质是**权衡（Trade-off）**的艺术。

**它不是算法题**：没有唯一答案，而是在"性能、成本、复杂度、一致性"之间做取舍。

**比喻**：系统设计 = **设计一座城市**。不只是盖一栋楼（写一个功能），而是规划：主干道（网络）、供水（数据）、消防（容灾）、人口增长（扩展）。城市会根据人口规模（用户量）决定要不要修地铁（引入缓存/消息队列）。

### 4.2 系统设计四步法（通用流程）

面对任何系统设计题，按这个流程走：

```
① 澄清需求 → 功能是什么？用户量多少？数据规模多大？
② 估算规模 → 每天多少请求？需要多少存储？
③ 设计架构 → 画出组件图：前端/后端/数据库/缓存/消息队列
④ 深入细节 → 解决瓶颈：加缓存？分库分表？加副本？
```

**关键一步：规模估算**。用简单的数学估算量级，比如：

> 假设日活 10 万用户，每人每天发 10 条动态 → 日写入 100 万条 → 每秒约 12 条（1000000/86400）。这个量级**单库就扛得住**，不需要分布式。但如果每秒 1 万条，就要引入消息队列 + 分片了。

**为什么先估算**：**规模决定架构**。500 用户的系统用 Redis + 分库分表就是浪费；百万并发的系统用单台 Flask 就是自杀。

### 4.3 核心概念：垂直扩展 vs 水平扩展

| 方案 | 做法 | 比喻 | 优点 | 缺点 |
|------|------|------|------|------|
| **垂直扩展** | 升级单台机器（加 CPU/内存） | 把一个小店厨房换成更大的 | 简单、不改造代码 | 有物理上限、成本高（8 核翻 16 核价格翻倍不止） |
| **水平扩展** | 加更多机器（集群） | 开连锁店，多家分店 | 几乎无限扩展、按需加 | 要改造架构（无状态化、负载均衡） |

**关键前提——无状态化**：要水平扩展，后端必须**无状态**——任何请求打到任何一台机器结果都一样。Session 存内存、进程内缓存都会破坏无状态。所以方案是：状态放 **Redis**（分布式缓存）、数据库在 **集群**，后端只留逻辑。

**你的项目现状**：单台服务器（垂直），Gunicorn 多 worker。未来人多了，第一步就是**水平扩展**：多台 Flask 进程 + Nginx 负载均衡 + 状态全部挪进 Redis/PostgreSQL。

### 4.4 负载均衡（Load Balancing）

**定义**：负载均衡把请求**分摊到多台服务器**，避免一台过载。

**比喻**：负载均衡 = **餐厅领位员**。顾客（请求）来了，领位员看哪桌（服务器）空就领到哪桌；某桌满了就安排去别的桌。

| 算法 | 做法 | 比喻 | 适用 |
|------|------|------|------|
| 轮询 Round Robin | 轮流分发给每台 | 轮流安排到 1、2、3 号桌 | 各台配置相同 |
| 加权轮询 | 按权重分发 | 大桌多接几人 | 机器性能不等 |
| 最少连接 | 发给连接最少的 | 找最空的桌 | 请求时长不均 |
| 哈希 | 按来源 IP/参数固定分配 | 老顾客固定坐老位置 | 需要会话保持 |

**你的项目里**：Nginx 就是负载均衡器（虽然目前只有一台后端，但架构已就位，加一台后端改下配置即可）。

### 4.5 消息队列（Message Queue）

**定义**：消息队列让生产者（Producer）把消息放进队列，消费者（Consumer）异步取走处理——**把同步请求变成异步处理**。

**比喻**：消息队列 = **快递公司**。

| 消息队列概念 | 快递公司类比 |
|-------------|------------|
| 生产者 Producer | 寄件人 |
| 队列 Queue | 快递仓库 |
| 消费者 Consumer | 收件人 |
| ACK 确认 | 签收确认 |
| 重试 Retry | 重新派送 |
| 死信队列 DLQ | 退件处 |

**什么时候该用消息队列**：
- **削峰**：秒杀/突发流量先丢进队列，后端慢慢消化，不让数据库瞬间被打爆。
- **解耦**：发帖后要通知关注者、发邮件、更新索引，这些不必同步完成，丢进队列异步做。
- **异步**：判题这种耗时任务，提交后立刻返回"排队中"，判完再通知。

**你的项目判题场景**：现在直接调 Glot.io 同步判题，用户要等结果。进阶方案：提交后丢进消息队列，判题 worker 异步处理，完成后前端轮询/推送状态——这就是消息队列最典型的使用。

**这个比喻的局限**：快递公司没有消息确认（ACK）、路由规则、优先级、持久化——消息队列都有，比快递公司"聪明"得多。

### 4.6 CAP 定理（分布式系统的"不可能三角"）

**CAP 定理**：分布式系统不可能同时满足三点：

| 字母 | 含义 | 解释 |
|------|------|------|
| **C** | Consistency 一致性 | 所有节点数据时刻相同 |
| **A** | Availability 可用性 | 每个请求都得到响应（即使数据旧） |
| **P** | Partition Tolerance 分区容错 | 网络中断时系统仍能工作 |

**定理内容**：网络分区（P）在真实分布式系统中**不可避免**，所以只能在 C 和 A 之间二选一：
- **CP**：分区时宁可拒绝服务，也要保证数据一致（如多数银行、ZooKeeper）。
- **AP**：分区时保证可用，但数据可能暂时不一致（如社交媒体的点赞数、新闻信息流——稍后同步即可，用户能接受短暂的"数字还没刷新"）。

**比喻**：两个仓库之间电话断了（网络分区），顾客来问库存。**CP** 的做法：电话不通就不卖（拒绝服务，但绝不卖超）；**AP** 的做法：照卖（可用），卖完可能发现另一个仓库也卖了（短暂不一致，稍后对账）。

**注意**：CAP 不是"任何时候三选二"，而是"**只在网络分区发生时才 C/A 二选一**"。网络正常时两者可以兼得。

### 4.7 一个完整案例：设计短链接系统

把学到的全部串起来，设计一个"长网址转短网址"系统：

**① 需求澄清**：功能 = 长 URL 变短码 + 短码跳回长 URL。规模 = 每天新增 1 亿条，读取是写入的 100 倍。

**② 估算**：每天 1 亿条 × 100 字节 ≈ 10GB/天，一年 3.6TB——需要分布式存储了。读 QPS ≈ 1亿×100/86400 ≈ 11.6 万/秒——必须缓存。

**③ 架构设计**：

```
用户 → 负载均衡(Nginx) → 后端集群(Flask, 无状态)
                              ├─ 写：PostgreSQL(分片) + 短码生成
                              ├─ 读：先查 Redis 缓存 → 未命中查 PostgreSQL
                              └─ 计数器/ID 生成：Redis INCR
```

**④ 关键细节决策**：
- **短码怎么生成**：用 Redis `INCR` 自增数字 → base62 编码（0-9a-zA-Z），6 位可表示 62⁶ ≈ 568 亿，够用。
- **读多写少**：读接口先查 Redis，命中率 95%+，数据库压力骤降。
- **一致性**：短码→长码几乎不变，缓存过期时间设长。
- **扩展**：后端无状态可水平扩展；PostgreSQL 按短码哈希分片。

**为什么这样设计**：每个决策都对应一个"为什么"——读多写少→缓存；写大→分片；无状态→可水平扩展。**面试考的就是你能不能说出这些为什么。**

> **思考题 4**：秒杀场景（1 万个用户抢 100 件商品）为什么必须用消息队列或 Redis 原子操作？直接让 1 万请求同时打数据库会怎样？

## 第五部分：源码阅读

### 5.1 为什么读源码？读什么？

**为什么读**：看懂别人写的好代码，是提升设计能力最快的路——比看教程有效得多。

| 收益 | 说明 |
|------|------|
| 理解原理 | 框架的"魔法"其实是代码，读完你就不怕它了 |
| 学习设计 | 高手怎么分层、怎么命名、怎么解耦 |
| 面试加分 | 面试官最爱问"你读过哪些源码" |
| 排错能力 | 出 bug 时能自己钻进框架内部找原因 |

**读什么（由易到难）**：

| 层级 | 例子 | 难度 | 建议 |
|------|------|------|------|
| 自己项目的代码 | 你的 OJ 项目 | ★ | 先读懂自己的 |
| 工具库 | 标准库、requests、Peewee | ★★ | 有具体使用场景 |
| 核心框架 | Flask、Vue | ★★★ | 读启动流程/核心机制 |
| 中间件 | Redis、Nginx、Celery | ★★★★ | 进阶 |

### 5.2 怎么读？六步方法论

```
① 先会用：把框架用熟练，带着"它怎么做到的"疑问
② 跑起来：下载源码，本地能跑，打断点观察
③ 找入口：从"你调用它的第一行"（如 app.run()、create_app()）开始
④ 画调用链：main → 函数A → 函数B → 函数C，标注每步做了什么
⑤ 抓核心：不逐行读，先抓主干；细节（如加锁、缓存）第二遍再看
⑥ 做笔记：把调用链画成图，写进你的笔记系统（Obsidian）
```

**最重要的心法**：**不要从头读到尾**。源码是按"主流程"组织的，你要**跟着数据流走**，只关注主线，分支细节跳过，回头再补。

**比喻**：读源码 = **拆解一台引擎**。不是把每个螺丝都拧下来，而是先搞清楚"油箱→泵→喷油嘴→气缸→排气"这条**燃料流动主线**，其他零件围绕主线理解。

### 5.3 工具：Debugger 断点调试

读源码最有效的工具不是"看"，是**调试器**。

**断点（Breakpoint）**：在代码某行停住，逐行执行、看变量变化。VS Code / PyCharm 都内置。

**调试三步**：
```
① 在入口函数第一行打断点
② 单步执行（Step Over 不进入子函数 / Step Into 进入子函数）
③ 观察调用栈（Call Stack）——看"我是怎么走到这里的"
```

**比喻**：断点 = 行车记录仪的**回放**。出了事故（bug）或想搞懂流程，就回放到关键路口（断点）慢放看。

### 5.4 案例：读 Flask 的 `app.run()` 做了什么

用六步法拆解 Flask 启动流程：

**调用链**：
```
app.run()
 └─ Werkzeug 的 run_simple()
      ├─ 创建 WSGI server（监听端口）
      ├─ 加载应用（app:app）
      └─ 启动服务器循环：等请求 → 处理 → 响应
```

**读到什么（收获）**：
1. `app.run()` 本质是**启动一个 HTTP 服务器**，监听你指定的端口。
2. Flask 本身是 **WSGI 框架**——它把 HTTP 请求转成 Python 环境（environ），处理完把结果转回 HTTP 响应。
3. 生产环境换 Gunicorn 的原因：`app.run()` 的开发服务器是**单进程同步**的。

**为什么值得读**：读完你就明白"框架不是魔法，就是一堆 Python 代码"——自信心和排错能力都上去了。

### 5.5 案例：读 Vue 的响应式原理

**问题**：Vue 里你改 `data` 的值，页面自动更新，怎么做到的？

**核心原理（Proxy 代理）**：
```
① Vue 用 Proxy 包装你的 data 对象
② 当你"读"属性时 → 收集依赖（记下"谁在用这个属性"）
③ 当你"写"属性时 → 触发更新（通知所有用到它的组件重新渲染）
```

**源码入口**：Vue 源码 `packages/reactivity/src/reactive.ts` 里的 `reactive()` 函数 → `proxy()`。

**读到什么（收获）**：
1. 响应式 = **读时收集、写时通知**（依赖收集 + 发布订阅）。
2. 它本质是**设计模式"观察者模式"**的实现。
3. 了解这个，面试问"Vue 和 React 响应式区别"时你能讲到原理层。

### 5.6 读到什么程度算"读懂了"？

**检验标准（费曼检验）**：
1. 能**不看源码**画出自它的核心调用链。
2. 能给小白**讲清楚**"它是怎么工作的"。
3. 能回答"**为什么这么设计**"（权衡是什么）。
4. 能**改一处**并预测后果（比如把链表换成数组会怎样）。

**比喻**：读源码不是"读过"就完了，而是**拆过、装回去过、还能给别人讲清楚它为什么这样设计**——这才叫真读懂。

## 第六部分：常见误区

### 6.1 误区一：测试覆盖率 100% = 代码没问题

覆盖率只说明"哪些行被执行了"，不说明"行为是否正确"。100% 覆盖但全是无效断言，照样有 bug。**优先保证核心逻辑的测试质量，而不是追逐覆盖率数字**。

### 6.2 误区二：什么都缓存

缓存有成本：不一致风险、维护复杂度。**低频访问、强一致要求的数据不要缓存**。缓存要加在"读多写少、热点集中"的数据上。

### 6.3 误区三：Docker 里用 root 跑、把密钥写进 Dockerfile

容器默认是 root，被攻破后权限极大。**最佳实践**：镜像里建非 root 用户运行；密钥用环境变量/secret 注入，**绝不写进 Dockerfile**（会被提交进镜像和 Git）。

### 6.4 误区四：一上来就微服务、就分布式

你的项目现在是单机 + 单库，完全够用。**分布式是为解决规模问题引入的，不是炫技**。过早微服务化 = 把简单问题复杂化。先单机跑通，再按需演进。

### 6.5 误区五：读源码就是从头翻到尾

逐行从头读是效率最低的方式。**先跑起来 + 抓主流程 + 断点调试 + 画调用链**，比逐行阅读高效十倍。

### 6.6 误区六：Redis 里的 key 永远不会过期 / 缓存能解决一切性能问题

Redis 默认 key 不过期（除非你设置 TTL），**设计时必须有过期策略**，否则内存会涨满。另外缓存只解决"读"的性能，**写性能、慢 SQL、代码复杂度**要靠索引、事务、代码优化解决。

> **思考题 6**：你的 OJ 项目现在要在 Docker 里部署，如果某天用户量翻了 10 倍，你会按什么顺序做哪几件事？

## 附录 A：思考题参考答案

**思考题 1**：优先写**单元测试**。因为单元测试最便宜（快、稳、隔离）、数量可最多、能覆盖最多核心逻辑，且能支撑重构。集成测试/E2E 数量少且贵，可以后面补。测试金字塔的思想就是"底层（单元测试）数量最多最重要"。

**思考题 2**：Docker 构建按层缓存。`COPY requirements.txt` 单独一层，只要 requirements.txt 没变，`RUN pip install` 那一层就能命中缓存不重装依赖；如果把它和代码一起 `COPY . .`，任何代码改动都会导致这一层失效，每次都要重装所有依赖。

**思考题 3**：最可能发生**缓存穿透**——攻击者请求不存在的题目 ID，Redis 永远查不到（没有缓存），每次都打 PostgreSQL，把数据库拖垮。防御：**缓存空值**（把"不存在"也缓存 60 秒）、加**布隆过滤器**（用极小的内存判断"这个 ID 在不在"，不在直接拒绝）。

**思考题 4**：1 万个请求同时打数据库会瞬间耗尽数据库连接（你的连接池上限才 20），大量请求超时失败，甚至拖垮数据库。用**消息队列削峰**（1 万请求先进队列，后端每秒只处理几十个）或 **Redis 原子操作**（用 `DECR` 扣减库存，减到负数即抢完）保证库存不超卖且系统不崩。

**思考题 5**：先会用才能"带着问题读"——你清楚某个功能应该怎么用，才能判断源码是不是符合预期；没有使用经验直接读源码，会不知道哪些代码是关键路径、哪些是边缘分支，容易迷失在细节里，读完也记不住。

**思考题 6**：按这个顺序：① 后端**无状态化**（把进程内缓存/状态挪进 Redis）；② 加 **Redis 缓存**热点数据；③ **Nginx 负载均衡** + 水平扩展多台后端；④ PostgreSQL 加**索引优化** + 连接池调优；⑤ 判题改**异步消息队列**；⑥ 数据库分片/读写分离（最后才考虑）。每一步都要先测再上，避免引入新问题。
