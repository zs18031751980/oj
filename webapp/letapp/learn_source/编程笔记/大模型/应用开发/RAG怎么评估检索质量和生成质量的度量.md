# `# RAG怎么评估?检索质量和生成质量的度量 

上一篇《RAG优化思路:Query改写、混合检索、Rerank、父子块检索、Context压缩》讲了Query改写、混合检索、Rerank这些常见优化手段。 

但到了真实项目里,还有一个问题绕不开:**你怎么知道优化有没有效果?** 

很多录友做RAG优化全凭感觉——"加了Rerank感觉好多了"、"换了Embedding模型好像更准了"。面试官追问:"你们怎么量化优化效果?",一下就卡壳了。 

面试官问:"你们RAG系统怎么评估?用什么指标?" 

很多录友会回答:"我们看召回率,还会人工抽查一些答案质量。" 

这个回答方向不算错,但问题在于:**召回率具体怎么算?人工抽查的标准是什么?生成质量用什么维度衡量?** 

真正做过RAG评估的人会知道,评估分两层:**检索侧评估**和**生成侧评估**。检索侧要看召回率、精准率、排序质量;生成侧要看答案忠实度、相关性、上下文利用率。没有这套完整的评估体系,所有优化都是盲猜。 

## `# 简要回答 

RAG评估分为**检索侧评估**和**生成侧评估**两个层次,每一层都有对应的核心指标: 

**检索侧评估**:衡量检索系统能不能找到正确的文档片段。 
  - **召回率(Recall@K)**:正确答案在top-K结果中出现的比例,衡量"相关内容有没有被找到"   - **精准率(Precision@K)**:top-K结果中相关内容的比例,衡量"找到的内容有多少是相关的"   - **MRR(Mean Reciprocal Rank)**:第一个正确结果的排名倒数均值,衡量"最相关的结果排在哪"   - **NDCG(Normalized Discounted Cumulative Gain)**:考虑排序位置和相关度等级的综合排序质量指标 

**生成侧评估**:衡量最终生成的答案质量。 
  - **忠实度(Faithfulness)**:答案是否忠实于检索到的上下文,有没有幻觉   - **答案相关性(Answer Relevancy)**:答案是否真正回答了用户的问题   - **上下文相关性(Context Relevancy)**:检索到的上下文对回答问题是否有用   - **上下文召回(Context Recall)**:生成答案所需的关键信息是否都在检索到的上下文中 

一句话:**检索侧保证能找到,生成侧保证用得好。没有评估的优化,就是拿着锤子找钉子。** 

## `# 详细回答 

### `# 为什么RAG必须有评估体系? 

很多团队做RAG优化是这样的:**换个Embedding模型试试→感觉好点了→上线**。问题出在哪? 
  - **无法量化优化效果**:不知道这次改动让效果提升了5%还是50%,也不知道在哪些场景提升了、哪些场景变差了   - **无法对比不同方案**:A方案用混合检索,B方案用Rerank,到底哪个更适合当前业务?没有评估就只能猜   - **无法发现退化**:加了新功能后,老场景的效果有没有变差?没有评估就发现不了   - **面试答不上**:面试官问"你们怎么验证优化有效",只能说"感觉更好了",这不是工程师的回答 

**真正的工程化RAG,必须先建立评估体系,再做优化。** 这是应用开发和"调API玩玩"的本质区别。 

### `# 检索侧评估:能不能找到相关内容? 

检索侧评估关注一个核心问题:**用户问题对应的正确答案片段,有没有出现在检索结果里?排在什么位置?** 

![检索评估四大指标](../images/file1.kamacoder.com/i/web/20260721194159_01.png)
 

这张图展示了检索评估的四个核心指标如何从不同角度衡量检索质量:Recall看覆盖、Precision看纯度、MRR看首位、NDCG看排序。 

#### `# 召回率(Recall@K) 

**定义**:在top-K个检索结果中,正确答案片段出现的比例。 

公式: `Recall@K = (检索到的相关chunk数) / (所有相关chunk总数)` 

举个例子:用户问"公司年假政策是什么?",知识库里有3个chunk包含正确答案。如果检索top-5结果里包含了其中2个,那么`Recall@5 = 2/3 = 66.7%`。 

**Recall的工程意义**: 
  - **Recall低(<70%)说明检索侧有严重问题**,相关内容根本没被找到,后面生成再好也没用   - Recall是检索系统的第一道防线,Recall不够,加Rerank也救不回来   - 优化Recall的方向:改进Embedding模型、调整Chunk策略、引入混合检索、扩大top-K 

**Recall的局限**:只看"找没找到",不管"找到了多少垃圾"。如果top-100里包含了所有正确答案,Recall@100 = 100%,但这99%的噪声会严重干扰生成质量。 

#### `# 精准率(Precision@K) 

**定义**:top-K个检索结果中,相关内容占的比例。 

公式: `Precision@K = (检索到的相关chunk数) / K` 

还是上面的例子:top-5结果里有2个相关chunk,那么`Precision@5 = 2/5 = 40%`。 

**Precision的工程意义**: 
  - **Precision低说明噪声太多**,检索结果里大部分是不相关内容,会稀释模型注意力   - Precision和Recall是一对矛盾:扩大K可以提高Recall,但会降低Precision   - 优化Precision的方向:加Rerank精排、收紧检索阈值、改进相似度计算 

**实际工程中的平衡**:通常会先用较大的K(比如20-50)保证Recall,再通过Rerank把Precision拉回来,最终只传3-5个高质量chunk给LLM。 

#### `# MRR(Mean Reciprocal Rank) 

**定义**:第一个相关结果的排名倒数,在多个查询上取平均。 

公式: `MRR = (1/N) * Σ(1/rank_i)`,其中`rank_i`是第i个查询的第一个相关结果的排名。 

举例:3个查询,第一个相关结果分别排在第1、第3、第2位,那么`MRR = (1/1 + 1/3 + 1/2) / 3 = 0.611`。 

**MRR的工程意义**: 
  - **衡量"最相关的结果是否排在前面"**,对用户体验影响很大   - 搜索引擎、推荐系统常用这个指标,因为用户往往只看前几条结果   - 在RAG场景,如果最相关的chunk排在top-1,模型更容易抓住核心信息 

**MRR vs Recall**:Recall关注"有没有找全",MRR关注"最好的有没有排前面"。两者都重要,但侧重不同。 

#### `# NDCG(Normalized Discounted Cumulative Gain) 

**定义**:考虑排序位置和相关度等级的综合排序质量指标。 

这是最复杂但也最全面的检索评估指标。核心思想: 
  - **相关度分级**:不是简单的"相关/不相关",而是给每个结果打分(如0-3分,3分最相关)   - **位置折扣**:排在前面的结果权重更高,排在后面的被"折扣"   - **归一化**:和理想排序(所有相关结果按分数从高到低排列)对比,得到0-1之间的分数 

公式: `DCG@K = Σ(rel_i / log2(i+1))`,其中`rel_i`是第i个位置结果的相关度分数。 

`NDCG@K = DCG@K / IDCG@K`,`IDCG`是理想情况下的DCG。 

**NDCG的工程意义**: 
  - **综合评估排序质量**,既考虑相关性,又考虑排序位置   - 适合需要精细评估的场景,比如对比不同检索算法、评估Rerank效果   - 计算成本高(需要人工标注相关度等级),通常用于离线评估 

**什么时候用NDCG**:当你需要精确对比两个检索方案的排序质量差异时。日常监控更多用Recall和MRR,因为标注成本低。 

### `# 生成侧评估:答案质量怎么衡量? 

检索侧保证找到了相关内容,但**最终答案质量如何**,还需要生成侧评估。 

生成侧评估的难点在于:**答案是自然语言,没有标准答案,很难用简单公式衡量。** 早期只能靠人工评估,成本高、不可扩展。 

RAGAS(Retrieval Augmented Generation Assessment)框架提出了一套基于LLM的自动化评估方法,目前已经成为RAG生成评估的事实标准。 

![RAGAS框架四维度](../images/file1.kamacoder.com/i/web/20260721194201_02.png)
 

这张图展示了RAGAS框架的四个核心维度如何从不同角度评估生成质量:Faithfulness防幻觉、Answer Relevancy看回答、Context Relevancy看检索、Context Recall看覆盖。 

#### `# Faithfulness(忠实度) 

**定义**:生成的答案是否忠实于检索到的上下文,有没有编造事实。 

**评估方法**: 
  - 把生成的答案拆分成多个陈述(statements)   - 用LLM判断每个陈述能否从上下文中推导出来   - 计算`Faithfulness = (可推导陈述数) / (总陈述数)` 

举例: 
  - 上下文:"公司年假为10天,工龄满3年增加到15天。"   - 生成答案:"公司年假为10天,满3年可增加到15天,满5年可增加到20天。"   - 前两个陈述可从上下文推导,第三个陈述("满5年20天")是编造的   - `Faithfulness = 2/3 = 66.7%` 

**Faithfulness的工程意义**: 
  - **衡量RAG是否真正"Grounded"(有根据的)**,这是RAG相比纯LLM的核心优势   - Faithfulness低说明模型在自由发挥,没有严格基于检索结果回答   - 优化方向:改进Prompt约束("请严格根据以下资料回答")、使用更强的模型、减少上下文噪声 

#### `# Answer Relevancy(答案相关性) 

**定义**:生成的答案是否真正回答了用户的问题,有没有答非所问。 

**评估方法**: 
  - 用LLM根据生成的答案,反向生成N个可能的问题   - 计算这N个问题和原始问题的语义相似度   - 相似度越高,说明答案越切题 

公式: `Answer Relevancy = (1/N) * Σ similarity(original_query, generated_query_i)` 

举例: 
  - 原始问题:"公司年假政策是什么?"   - 生成答案:"公司实行弹性工作制,员工可以远程办公。年假为10天。"   - LLM反向生成的问题可能是:"公司工作制度是什么?",和原问题相似度低   - Answer Relevancy低,说明答案偏题了(虽然提到了年假,但重点跑偏了) 

**Answer Relevancy的工程意义**: 
  - **衡量答案是否切题**,防止模型给出"相关但不精准"的答案   - 低分说明模型理解问题有偏差,或者上下文干扰了判断   - 优化方向:优化Prompt明确回答要求、改进Query理解、减少无关上下文 

#### `# Context Relevancy(上下文相关性) 

**定义**:检索到的上下文中,有多少内容对回答问题是真正有用的。 

**评估方法**: 
  - 用LLM从检索到的每个chunk中提取和问题相关的句子   - 计算`Context Relevancy = (相关句子数) / (总句子数)` 

举例: 
  - 问题:"公司年假政策?"   - 检索到的chunk:"公司成立于2010年,主营业务是软件开发。员工福利包括五险一金、年假10天、节日礼品。公司地址在北京朝阳区。"   - 只有"年假10天"这一句相关,其余都是噪声   - `Context Relevancy = 1/4 = 25%` 

**Context Relevancy的工程意义**: 
  - **衡量检索质量和Chunking质量**,低分说明检索到了很多无关内容   - 这是检索侧评估的补充,从生成角度反向评估检索效果   - 优化方向:改进Chunking策略(chunk太大会包含太多无关内容)、加Rerank、减少top-K 

#### `# Context Recall(上下文召回) 

**定义**:ground truth答案中的关键信息,有多少出现在检索到的上下文中。 

**评估方法**: 
  - 需要有标注的标准答案(ground truth)   - 用LLM判断标准答案中的每个陈述是否能从上下文中推导出来   - 计算`Context Recall = (可从上下文推导的陈述数) / (标准答案总陈述数)` 

举例: 
  - 问题:"公司年假政策?"   - 标准答案:"基础年假10天,工龄满3年增加到15天。"(2个陈述)   - 检索上下文只提到"基础年假10天",没提工龄相关内容   - `Context Recall = 1/2 = 50%` 

**Context Recall的工程意义**: 
  - **从生成角度评估检索完整性**,补充检索侧Recall指标   - 低分说明检索漏掉了关键信息,即使生成效果再好也无法给出完整答案   - 优化方向:扩大top-K、改进检索算法、检查索引覆盖 

### `# RAGAS四个指标的关系 

这四个指标从不同角度评估RAG系统: 
  - **Context Recall + Context Relevancy** = 检索质量(从生成角度看)   - **Faithfulness + Answer Relevancy** = 生成质量 

理想情况: 
  - Context Recall高 → 检索找全了关键信息   - Context Relevancy高 → 检索结果干净,噪声少   - Faithfulness高 → 模型忠实基于检索结果回答   - Answer Relevancy高 → 答案切题,没有跑偏 

如果Context Recall低,后面其他指标再高也没用,因为关键信息根本没检索到。 

如果Context Relevancy低,会拉低Faithfulness和Answer Relevancy,因为噪声太多干扰了生成。 

### `# 如何构建RAG评估集? 

说了这么多指标,但**怎么计算这些指标?**核心是要有一个**评估数据集**。 

评估集需要包含: 
  - **问题(Query)**:用户可能问的问题   - **标准答案(Ground Truth)**:可选,用于Context Recall评估   - **相关文档片段(Relevant Chunks)**:用于检索侧Recall/Precision评估 

**构建评估集的三种方法**: 

**方法1:人工构造**(质量最高,成本最高) 
  - 挑选业务中的高频问题   - 人工标注每个问题的正确答案和相关chunk   - 适合核心业务场景,通常构建50-200条即可建立baseline 

**方法2:真实日志采样**(质量中等,成本中等) 
  - 从生产环境日志中采样真实用户问题   - 人工标注答案质量(好/中/差)   - 适合持续监控,发现线上问题 

**方法3:LLM生成**(质量较低,成本最低) 
  - 用LLM根据知识库内容生成问题-答案对   - 适合快速验证,但要注意LLM生成的问题可能过于理想化,不代表真实用户行为 

**工程实践建议**: 
  - 先用方法3快速搭建评估框架   - 再用方法1构建核心场景的高质量评估集(50-100条)   - 用方法2持续补充,逐步扩大评估覆盖 

### `# 离线评估 vs 在线评估 

**离线评估**:在测试集上跑指标,优化前后对比。 
  - 优点:可控、可重复、成本低   - 缺点:测试集可能不代表真实场景 

**在线评估**:真实用户使用时收集反馈。 
  - 显式反馈:用户点赞/点踩、提交纠错   - 隐式反馈:用户是否继续追问、是否复制答案、停留时长 

**工程实践**: 
  - 用离线评估指导优化方向   - 用在线评估验证真实效果   - 两者结合,离线评估是必要条件,在线评估是充分条件 

### `# 评估驱动的优化闭环 

有了评估体系,RAG优化就不再是盲目试错,而是形成闭环: 

![评估驱动优化闭环](../images/file1.kamacoder.com/i/web/20260721194203_03.png)
 

这张图展示了基于评估的RAG优化闭环:从建立baseline开始,通过评估定位问题,针对性优化,再次评估验证,形成数据驱动的迭代循环。 

**第一步:建立baseline** 
  - 在评估集上跑一遍当前系统,记录所有指标   - 这是后续所有优化的对比基准 

**第二步:定位瓶颈** 
  - 如果Recall@5 < 70%,优先优化检索召回   - 如果Recall高但Precision低,加Rerank   - 如果Context Relevancy低,优化Chunking或减少top-K   - 如果Faithfulness低,改进Prompt约束   - 如果Answer Relevancy低,检查Query理解和模型能力 

**第三步:针对性优化** 
  - 每次只改一个变量(比如只换Embedding模型,其他不动)   - 在评估集上重新跑指标 

**第四步:对比验证** 
  - 新指标比baseline好 → 采纳   - 新指标更差或某些场景退化 → 回滚或继续调整 

**第五步:持续迭代** 
  - 新问题加入评估集   - 定期重新评估   - 监控线上指标变化 

这才是工程化的RAG优化。 

## `# 知识拓展 

**Q1:检索评估一定要人工标注相关chunk吗?** 

不一定。如果有标准答案,可以用LLM判断"标准答案能否从某个chunk推导出来",自动化标注相关性。但核心场景建议还是人工标注一部分,作为评估的"黄金标准"。 

**Q2:RAGAS评估依赖LLM判断,会不会不准?** 

RAGAS用LLM做评估,确实可能有偏差。工程实践是:在核心评估集上对比LLM评估和人工评估的一致性,如果一致性高(比如85%以上),就可以信任LLM评估做大规模自动化。如果一致性低,说明评估Prompt需要调整,或者这个场景确实需要人工介入。 

**Q3:Recall和Precision哪个更重要?** 

要看业务场景。如果答不上来的代价很高(比如医疗、法律咨询),Recall更重要,宁可多召回一些,也不能漏掉关键信息。如果噪声的代价很高(比如客服机器人给错答案会被投诉),Precision更重要,宁可少答,也不能答错。通常的做法是:用大K保Recall,用Rerank保Precision,两头都要。 

**Q4:评估集要多大才够?** 

取决于业务复杂度。简单场景(FAQ类),50-100条可以建立可信的baseline。复杂场景(开放域问答),可能需要300-500条才能覆盖主要case。不要贪多,先从核心高频场景开始,逐步扩展。关键是评估集要**有代表性**,而不是一味追求数量。 

**Q5:怎么在面试中快速讲清RAG评估?** 

按三层结构:**检索侧指标(Recall/Precision/MRR)+ 生成侧指标(RAGAS四维度)+ 评估驱动优化闭环**。先说清楚评估分两侧,每侧核心看什么;再说怎么建评估集、怎么形成优化闭环。最后举个例子:"我们发现Recall@5只有65%,优化Embedding模型后提升到82%,再加Rerank后Precision从30%提升到70%,最终答案的Faithfulness从0.75提升到0.88"——有框架、有数据、有闭环,这就是好回答。 

**Q6:开源工具怎么选?** 
  - 检索评估:自己写脚本计算Recall/Precision/MRR比较简单,也可以用`ranx`库   - RAGAS评估:直接用`ragas`库,已经实现了四大指标的LLM评估逻辑,支持多种LLM后端   - 评估集管理:可以用`LangSmith`或`Weights & Biases`做实验跟踪和对比
