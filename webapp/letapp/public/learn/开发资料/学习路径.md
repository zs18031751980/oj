## 一、软件开发通用知识（地基）

**核心结论**：软件开发是"地基"，网站开发是"建在上面的一栋楼"。先打好地基，再学建楼，事半功倍。地基共 5 块：语言、数据结构与算法、计算机基础、数据库、版本控制。

### 1.1 编程语言——你的"表达工具"

**定义**：编程语言是你和计算机沟通的桥梁。计算机只懂机器码（0 和 1），编程语言让你用接近人类的文字写出指令，再翻译给计算机执行。

**原理——两种翻译方式**：

| 方式 | 代表语言 | 过程 | 比喻 | 特点 |
|------|---------|------|------|------|
| 编译型 | C、Go、Java | 一次性把全部代码翻译成机器码再运行 | 翻译整本书再阅读 | 运行快，但改代码要重新编译 |
| 解释型 | Python、JavaScript | 边翻译边执行 | 同声传译 | 开发快，但运行稍慢 |

**⭐ 你项目里就在这里**：前端 TypeScript（编译到 JS）通过 Vite 打包；后端 Python（Flask）是解释型语言。

**应用**：
- 做网站**必学 JavaScript**——它是浏览器唯一原生支持的编程语言。
- 后端可选 **Python / Java / Go / Node.js**。你现在用 Python，非常合适——语法接近自然语言，新手友好。
- **比喻**：Python 像用乐高拼房子（语法块直观）；C 像从烧砖开始盖房（更底层、更难）。

**常见误区**：以为"学了很多门语言 = 厉害"。实际上**精通一门 + 理解原理，迁移到其他语言只要 1-2 周**。语言是工具，思想是核心。

### 1.2 数据结构与算法——你的"工具箱"

**定义**：数据结构是组织数据的方式，算法是处理数据的步骤。

**核心数据结构**（每个都必须懂）：

| 结构 | 比喻 | 核心操作复杂度 | 适用场景 |
|------|------|--------------|---------|
| 数组 | 一排储物柜，按编号取放 | 随机访问 O(1) | 已知长度的同类型数据 |
| 链表 | 寻宝线索链，每条线索指向下一条 | 插入/删除 O(1)，查找 O(n) | 频繁增删、无随机访问需求 |
| 栈（LIFO） | 一摞盘子，只能从顶部取放 | 压入/弹出 O(1) | 函数调用、浏览器后退、括号匹配 |
| 队列（FIFO） | 食堂排队，先到先服务 | 入队/出队 O(1) | 任务调度、消息队列 |
| 哈希表 | 电话簿，按姓名直接查号码 | 查找 O(1) 均摊 | 字典、缓存、去重 |
| 树 | 公司组织架构图 | 查找 O(log n)（平衡树） | 目录结构、数据库索引 |
| 图 | 地铁线路图 | 遍历 O(V+E) | 社交网络、路线规划 |

**为什么重要**：同样的任务，用错数据结构，性能可能差几百倍。**比喻**：去图书馆找书——没分类（线性查找 O(n)）和按编号索引（树/哈希 O(log n)）相比，藏书越多差距越大。

**必学算法**：
- 排序：快速排序、归并排序（理解分治思想）
- 查找：二分查找
- 递归与分治
- 动态规划入门（背包问题是最经典入门题）

**⭐ 你项目里就在这里**：
- `submissions` 表按 `(problem_id, status)` 建索引 = 数据库里的"树/哈希"加速查询。
- 判题时要对比用户输出与期望输出，本质是字符串比较算法。
- Redis 缓存公告列表 = 哈希表思想的实践。

**常见误区**：以为算法 = 面试造火箭。实际上算法训练的是**分解问题、评估复杂度**的思维，是区分"能写"和"写得好"的分水岭。

### 1.3 计算机基础——你的"硬件直觉"

这一层看似与写业务代码无关，但遇到性能、并发、安全问题时，全是它派上用场。

**操作系统原理**：
- 进程与线程：进程是运行的独立程序，线程是进程内的执行单元。
- **比喻**：操作系统像酒店大堂经理——分配房间（内存）、安排入住退房（进程调度）、处理房间冲突（锁与并发）。
- 并发与锁：多个线程同时改同一数据会冲突，需要锁保护。**比喻**：两个人同时想在同一个 Excel 单元格写字，必须一人写完另一人再写。
- **⭐ 你项目里就在这里**：`DB_MAX_CONNECTIONS=20` 是数据库连接池上限——并发超过 20 个请求时会排队等待，这就是操作系统"资源有限，排队分配"思想的数据库版。

**计算机网络**：
- 分层模型：应用层（HTTP）→ 传输层（TCP/UDP）→ 网络层（IP）→ 链路层。
- **比喻**：网络协议像邮政系统——IP 是地址，TCP 是挂号信（保证送达、有序），UDP 是平信（快但不保证）。
- DNS：把域名翻译成 IP。**比喻**：通讯录——记住"www.xxx.com"这种名字，翻译成服务器 IP 才能找到。
- **⭐ 你项目里就在这里**：`https://ojapi.xauat.site` 通过 DNS 解析到服务器 IP；`ALLOWED_ORIGINS` 是 CORS（跨域）配置，本质是浏览器基于 HTTP 的安全机制。

### 1.4 数据库——你的"记忆仓库"

**定义**：数据库是专门存储和检索数据的软件。

**原理**：数据以**表**的形式存储，行是记录，列是字段。**比喻**：Excel 但更强大——支持多表关联、并发读写、按条件查询、事务回滚。

**两大类型**：

| 类型 | 代表 | 比喻 | 适合场景 | 局限 |
|------|------|------|---------|------|
| 关系型 | MySQL、PostgreSQL | 严格的表格，字段固定 | 交易、订单等需要一致性的场景 | 水平扩展难 |
| 非关系型 | MongoDB、Redis | 灵活的 JSON 文档 | 日志、缓存、高并发读取 | 事务与一致性较弱 |

**必须学的 SQL**（增删改查）：
- `SELECT ... FROM ... WHERE ...`（查）
- `INSERT INTO ...`（增）
- `UPDATE ... SET ...`（改）
- `DELETE FROM ... WHERE ...`（删）
- **比喻**：SQL 像向图书管理员提问——"SELECT * FROM 书 WHERE 作者='鲁迅'"就是"把所有鲁迅的书给我"。

**事务（ACID）**：一组操作要么全部成功、要么全部失败。**比喻**：转账——扣 A 的钱和加 B 的钱必须同时成功，否则钱就凭空消失了。

**⭐ 你项目里就在这里**：
- PostgreSQL 存储 6 张表：`users / problems / testcases / user_codes / submissions / announcements`，正是"表 = 关系型数据"的实践。
- Peewee 是 ORM（对象关系映射）——把数据库表映射成 Python 类，写代码不用拼 SQL 字符串。
- Redis 存 JWT 缓存、限流、公告缓存 = 非关系型数据库（键值对）的应用。

**常见坑——N+1 查询**：查 100 个用户，却发起了 101 次查询（1 次查用户列表 + 100 次查每个用户的订单）。**比喻**：取 100 份快递，每份都跑一趟仓库，而不是一趟搬回来。解决：用 `JOIN` 或预加载。

### 1.5 Git 版本控制——你的"时光机"

**比喻**：Git 是开发者的**游戏存档 / 时光机**。

| Git 概念 | 比喻映射 | 说明 |
|---------|---------|------|
| 提交 commit | 存档点 | 保存当前状态，可随时回到这里 |
| 分支 branch | 平行宇宙 | 不同分支互不影响，各自发展 |
| 合并 merge | 合并存档 | 把平行宇宙的内容合到一起 |
| 回滚 revert/reset | 读档 | 回到过去的某个存档 |
| .gitignore | 保险柜 | 不放进存档的东西（如密钥、`.env.local`） |

**原理**：每次提交保存的不是文件副本，而是**文件之间的差异（diff）**，像只记录"这一帧改了什么"，省空间。

**局限说明**：游戏存档没有合并冲突，而 Git 多人同时改同一文件时会产生冲突，需要手动解决。

**⭐ 你项目里就在这里**：`.env.local`（含密钥）**不被 Git 追踪**，正是 .gitignore 的应用；"提交 → push → 服务器拉取 → 重启"就是 Git 驱动部署的完整流程。

## 二、网站开发特化知识（大楼）

**总比喻**：**网站像一个餐厅**。

| 网站部件 | 餐厅类比 | 技术 |
|---------|---------|------|
| 浏览器 | 顾客去吃饭 | 前端渲染 |
| 网页内容 | 招牌、菜单 | HTML/CSS/JavaScript |
| 后端服务器 | 厨师 | 处理请求、返回数据 |
| 数据库 | 食材仓库 | 数据存储 |
| HTTP 请求 | 点菜流程 | 前后端通信 |

### 2.1 前端三件套（网站的门面）

| 技术 | 作用 | 比喻 | 你项目里的对应 |
|------|------|------|--------------|
| HTML | 网页的骨架/结构 | 房子的承重墙和房间布局 | Vue 模板 / .vue 文件 |
| CSS | 网页的样式/外观 | 墙纸、油漆、家具摆放 | Tailwind CSS 4 |
| JavaScript | 网页的行为/交互 | 电灯开关——一按就有反应 | TypeScript + Vue 3 |

**原理**：浏览器加载 HTML → 按 CSS 渲染样式 → 执行 JS 实现交互。三者缺一不可。

**工作流程**：你写的代码 → 浏览器解析 → 生成页面元素树（DOM）→ 用户交互触发事件 → JS 修改 DOM → 页面更新。

**现代框架（Vue/React）**：
- **比喻**：框架像预制房——不用每块砖都自己搬，直接拼装模块。
- 数据绑定：页面自动跟随数据变化更新，不用手动操作 DOM。
- 组件化：把页面拆成可复用的"零件"。

**⭐ 你项目里就在这里**：
- Vue 3 组合式 API + `<script setup>`。
- Pinia = 前端状态管理（多个页面共享的登录状态、主题偏好）。
- Vue Router = 页面路由（URL 与页面组件的对应关系）。
- Naive UI = 现成 UI 组件库（按钮、表格、弹窗）。
- Monaco Editor = 代码编辑器组件（在线编程的核心）。

**前端构建与打包**：
- Vite 是构建工具：开发时热更新，生产时打包优化。
- **⭐ 你项目里就在这里**：`monaco-editor` 体积大（约 3.7MB），已拆分为独立 `vendor-monaco` chunk 并按需加载——这是性能优化的实战经验。

### 2.2 HTTP 与网络协议（前后端的通信规则）

**定义**：HTTP（HyperText Transfer Protocol，超文本传输协议）是浏览器和服务器之间对话的"语言规则"。

**原理——点外卖流程**：
1. 顾客（浏览器）发请求："我要一份宫保鸡丁"（HTTP 请求）
2. 餐厅（服务器）回应："好的，这是你的菜"（HTTP 响应）

**请求方法**（"动词"）：
- GET：看菜单（只读，不改变状态）
- POST：下单（创建资源）
- PUT / PATCH：改菜（更新资源）
- DELETE：撤单（删除资源）

**状态码**（"应答结果"）：
- 2xx 成功：200 OK（菜好了）
- 3xx 重定向：302（请你移步另一窗口）
- 4xx 客户端错误：404（菜不在菜单上）、401（没验会员卡）、403（会员卡没权限）
- 5xx 服务器错误：500（后厨炸了）、502/503（后厨繁忙）

**比喻局限说明**：HTTP 是**无状态**的——服务器记不住你上次点了什么。要记忆就要用 Cookie/会话，像餐厅给你**手环编号**，下次报号码就知道你常吃辣。

**⭐ 你项目里就在这里**：
- 前端调用 `/code/run`、`/submissions/` 等接口，就是 HTTP 请求。
- JWT 令牌通过 `Authorization: Bearer <token>` 请求头传递 = "手环编号"。
- `FRONTEND_URL` 与 `ALLOWED_ORIGINS`（CORS）解决跨域：浏览器规定"跨域请求需服务器白名单许可"，像餐厅规定"非本店会员不能点外卖到家"。
- Swagger（`/auth` 等接口文档）让你可视化调试每个 HTTP 接口。

**会话 vs 令牌（JWT）**：

| 方案 | 原理 | 比喻 | 优缺点 |
|------|------|------|--------|
| Session 会话 | 服务端存会话，浏览器存 Session ID | 餐厅前台存你的订单记录，你拿着号牌 | 服务端可随时撤销，但占内存 |
| JWT 令牌 | 服务端签发带签名的令牌，浏览器保存，服务端验签 | 带防伪章的会员卡 | 无状态、可扩展，但撤销难 |

### 2.3 后端（网站的"厨房"）

**职责**：处理请求、读写数据库、返回数据。**比喻**：后厨——接单、从仓库取食材、做好菜递给窗口。

**必须学的知识**：

| 知识 | 作用 | 比喻 | 你项目里的对应 |
|------|------|------|--------------|
| 后端框架 | 提供现成的"厨房设备" | 厨具套餐 | Flask 3 + Flask-RESTX |
| API 设计 | 定义"菜单"——前端点什么、后端怎么应答 | 菜单规范 | REST 风格，Swagger 文档 |
| 认证授权 | 登录验证 | 验会员卡 | JWT + OIDC + GitHub OAuth |
| 安全防护 | 防攻击 | 防下毒 | 中间件限流、角色权限校验 |

**后端分层架构**（重要设计思想）：
- Controller 层（接收请求、返回响应）→ Service 层（业务逻辑）→ Model 层（数据操作）。
- **比喻**：餐厅的三层分工——迎宾（Controller）、厨师（Service）、仓库管理员（Model）。
- 好处：职责清晰、可测试、可替换。
- **⭐ 你项目里就在这里**：`controllers/ → services/ → models/` 正是这个分层，还有 `middleware/`（JWT 验证/角色权限/限流）、`interfaces/`（抽象接口 + 依赖注入）。

**依赖注入（DI）**：
- 定义：对象不自己创建依赖，而是由外部注入。**比喻**：厨师不用自己开农场，菜由采购部送进来。
- 好处：方便替换（测试时换成假数据）、方便复用。
- **⭐ 你项目里就在这里**：`core/`（DI 容器/服务配置）、`interfaces/`（ABC 抽象接口）就是 DI 的应用。

**常见后端陷阱**：
- SQL 注入：把用户输入直接拼进 SQL 字符串，攻击者可执行任意 SQL。**比喻**：点菜时"宫保鸡丁；再给我看后厨的保险柜密码"。**解决**：用 ORM 参数化查询（Peewee 天然防住）。
- XSS：把用户输入的 HTML/JS 原样渲染到页面，可窃取 Cookie。**比喻**：顾客在菜单上写"结账时把收银台的钱转给我"。**解决**：转义输出内容。
- N+1 查询：见 1.4 节。

### 2.4 网站部署（把菜端上桌）

| 概念 | 说明 | 比喻 |
|------|------|------|
| 服务器 | 把网站代码放到云服务器上 | 租店铺开业 |
| 域名 + DNS | 把域名翻译成服务器 IP | 通讯录 |
| Docker（容器化） | 把整个应用环境打包成"集装箱"（代码+依赖+配置） | 集装箱 |
| CI/CD | 自动构建、测试、发布 | 自动化流水线 |

**Docker 比喻展开**：

| Docker 概念 | 集装箱类比 | 说明 |
|------------|-----------|------|
| 镜像 Image | 装好货的集装箱模板 | 代码+依赖+配置的打包 |
| 容器 Container | 一个正在运输的集装箱 | 镜像运行起来的实例 |
| Dockerfile | 装箱单 | 描述怎么装货 |
| Docker 引擎 | 吊机/码头 | 负责装卸运行 |
| Docker Hub | 集装箱堆场 | 公共镜像仓库 |

**局限说明**：集装箱不支持分层构建，而 Docker 镜像支持分层（每层可缓存复用），比集装箱更灵活。

**部署流程（你的项目）**：
提交 → push → 服务器拉取 → 重启后端（Gunicorn 多 worker）+ 重新构建前端（Vite build）→ 静态服务器托管。

**什么是 Gunicorn**：Python Web 服务器，能同时处理多个请求（多 worker）。**比喻**：一个厨师忙不过来，雇好几个厨师同时做菜。Flask 自带的开发服务器只能单线程，生产环境必须换 Gunicorn。

## 三、工程化与进阶知识（精装修）

| 知识 | 内容 | 比喻 | 重要性 |
|------|------|------|--------|
| 测试 | 单元测试、集成测试、端到端测试 | 出厂前质检 | 高 |
| 设计模式 | 单例、工厂、观察者、依赖注入等 | 装修经典图纸，直接套用 | 中 |
| 缓存 | Redis、CDN | 书桌桌面：常用的放桌面，不常用的收进书架 | 高 |
| 消息队列 | RabbitMQ、Kafka | 快递公司 | 中 |
| 负载均衡 | Nginx 反向代理 | 餐厅领位员 | 中 |
| 监控与日志 | 结构化日志、指标、告警 | 后厨的摄像头和仪表盘 | 高 |

**重点比喻——消息队列 = 快递公司**：

| 消息队列概念 | 快递公司类比 |
|-------------|------------|
| 生产者 Producer | 寄件人 |
| 队列 Queue | 仓库 |
| 消费者 Consumer | 收件人 |
| ACK 确认 | 签收确认 |
| 重试 Retry | 重新派送 |
| 死信队列 DLQ | 退件处 |

**比喻局限说明**：快递公司不支持路由规则、优先级、消息持久化十年——消息队列支持。

**缓存原理（Redis）**：
- 为什么快：Redis 数据存在**内存**里（读写约 0.1ms），数据库存在**磁盘**上（约 1-10ms）。
- **比喻**：书桌桌面 = 内存（常用书放桌面），书架 = 磁盘（不常用的收进书架）。
- 缓存策略：读时先查缓存，未命中才查数据库并回填缓存；写时先更新数据库，再失效/更新缓存。
- **⭐ 你项目里就在这里**：公告列表 60s Redis 缓存，写操作时失效——正是"读缓存 → 写失效"的标准模式。

**限流**：
- 作用：防止某个用户短时间发大量请求打垮服务。
- **比喻**：餐厅限流 = 奶茶店"每人限购 2 杯"。
- **⭐ 你项目里就在这里**：`middleware/` 中有限流中间件，Redis 参与计数。

**设计模式一句话**：
- 单例：全局只允许一个实例（如数据库连接池）。
- 工厂：用一个方法生产对象，调用方不关心细节。
- 观察者：一个变化通知所有订阅者（如 Vue 的响应式系统本质）。
- **⭐ 你项目里就在这里**：`interfaces/` + `core/` DI 容器 = 工厂模式 + 依赖注入的组合。
